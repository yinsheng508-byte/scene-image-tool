## 二、现有代码梳理

## 2.1 前端核心状态与 UI 入口

### `desktop/renderer/puzzle/state.js`

当前 `AppState` 已包含与本次改造高度相关的字段：

- `generationMode`
- `singleFirstPuzzleOnce`
- `folderBindings`
- `shareSameFolderCycleInMultiFolder`
- `outputByPuzzleFolder`

这说明：

- 外层模式切换已有承载点
- 现有 `per-puzzle-folder` 子模式可以复用旧数据结构
- 新增子文件夹模式时不能直接替换这些字段，否则回归风险高

### `desktop/renderer/puzzle/ui-bindings.js`

当前已绑定：

- `assignFoldersBtn`
- `folderModal`
- `folderList`
- `folderSubdirToggle`
- `folderShareCycleToggle`

这说明现有弹窗骨架可复用，但需要新增：

- 子模式胶囊 DOM
- 子文件夹模式专属路径区 DOM
- 子文件夹模式说明文案和状态文本 DOM

### `desktop/renderer/index.html`

当前已有：

- 外层生成模式 radio
- 文件夹弹窗
- 左侧图片列表容器

这说明 HTML 层属于增量改造，不需要重做整体结构。

## 2.2 前端状态持久化与模板工作区

### `desktop/renderer/puzzle/index.js`

当前状态存取链路已经完整：

- `saveStateToStorage()`  
- `loadStateFromStorage()`
- `normalizeFolderBindings()`
- `normalizeTemplateWorkingSet()`
- `buildCurrentTemplateWorkingSet()`
- `restoreWorkingSetForTemplate()`

关键事实：

1. 当前不只是 `localStorage` 持久化，还有 `templateWorkingSets`
2. 工作区已经按模板隔离恢复
3. `folderBindings`、`outputByPuzzleFolder`、`shareSameFolderCycleInMultiFolder` 已进入工作区状态

这意味着：

- 新增子模式时，应该继续走“模板工作区状态”路线
- 不要把运行时文件夹状态写进模板本体

## 2.3 现有多文件夹弹窗与交互

### 当前关键函数

位于 `desktop/renderer/puzzle/index.js`：

- `handleAssignFolders()`
- `openFolderModal()`
- `renderFolderModalList()`
- `confirmFolderBindings()`
- `closeFolderModal()`

当前机制优点：

- 已有草稿态 `tempFolderBindings`
- 已有确认/取消边界
- 已有扫描文件夹并更新弹窗列表的能力

当前机制局限：

- 草稿态只覆盖 `folderBindings`
- 弹窗只有一种内容结构
- 所有 UI 逻辑都绑定在“逐拼图列表”模型上

因此本次改造不适合继续只维护一个 `tempFolderBindings`，需要升级为：

- 整个多文件夹弹窗的草稿态对象

---

## 2.4 左侧图片列表与预计生成数

### 左侧图片列表

`updateImageList()` 当前分两路：

- `single`：展示 `AppState.images`
- `multi-folder`：按 `AppState.puzzles + folderBindings` 分组展示

问题在于：

- 这里当前只有“扁平图片池”和“逐拼图文件夹池”两种数据源
- 子文件夹模式需要第三种数据源：`groups`

### 预计生成数

`updateEstimateCount()` 当前通过：

- `calculateEstimateCount(...)`

实际核心依赖：

- `buildTaskQueue(...)`

这意味着预计生成数天然可以通过真实任务队列长度驱动，不应该另写一套公式。

---

## 2.5 任务引擎

### `desktop/renderer/puzzle/generation-engine.js`

当前结构：

- `buildTaskQueue()`
- `buildSingleQueue()`
- `buildSingleQueueDefault()`
- `buildSingleQueueWithCover()`
- `buildMultiFolderQueue()`
- `calculateEstimateCount()`

这是整个改造的关键点。

现状优势：

- 单文件夹逻辑已经被封装成独立函数
- 多文件夹逻辑已有独立入口

本次最佳策略：

- 新增 `buildSubfolderBatchQueue()`
- 复用 `buildSingleQueue()`
- 不重写“单文件夹规则”

---

## 2.6 主进程扫描与导出

### `desktop/main.js`

当前扫描入口：

- `ipcMain.handle("puzzle:scanImages", ...)`

当前行为：

- 递归扫描整个目录
- 返回相对路径名

这不符合子文件夹模式要求，因此必须新增专用扫描 IPC。

当前导出入口：

- `ipcMain.handle("puzzle:generate", ...)`

当前逻辑特点：

- `outputByPuzzleFolder` 仅在 `generationMode === "multi-folder"` 时生效
- 勾选输出到子文件夹时，按 `puzzleId / puzzleName` 建目录
- 计数器也是按拼图页维度累计

这说明：

- 子文件夹模式导出时，必须扩展 payload 和 task 元数据
- 不能只靠当前 `puzzleName` 来判定输出目录

---

## 三、总体实施策略

采用“先状态与 UI，后任务引擎，再主进程导出，最后持久化与回归”的分阶段策略。

不建议一次性大改，原因：

- 弹窗、列表、队列、导出四条链路相互影响
- 如果同时改持久化和导出，回归问题难定位

建议总共拆为 6 个阶段：

1. 阶段0：基线整理与结构预留
2. 阶段1：前端状态模型与弹窗骨架
3. 阶段2：子文件夹模式扫描与左侧展示
4. 阶段3：任务引擎与预计生成数
5. 阶段4：主进程导出链路
6. 阶段5：持久化、模板工作区、回归收口

---

## 四、分阶段实施规划

## 阶段0：基线整理与结构预留

### 目标

在不改变现有用户行为的前提下，先为新子模式预留结构，降低后续改动耦合。

### 改动文件

- `desktop/renderer/puzzle/state.js`
- `desktop/renderer/puzzle/ui-bindings.js`
- `desktop/renderer/index.html`
- `desktop/renderer/puzzle/index.js`

### 具体任务

1. 在 `AppState` 中新增 `multiFolderConfig`
2. 保留旧字段，不立即删除：
   - `folderBindings`
   - `shareSameFolderCycleInMultiFolder`
   - `outputByPuzzleFolder`
3. 在 `index.html` 中加入弹窗子模式胶囊和子文件夹模式容器
4. 在 `ui-bindings.js` 中加入新 DOM 引用
5. 在 `index.js` 中建立统一弹窗草稿态对象，例如：

```javascript
let tempMultiFolderDraft = null;
```

### 本阶段不做

- 不接入真实扫描
- 不修改导出
- 不修改任务引擎

### 验收

- 页面能正常加载
- 现有 `per-puzzle-folder` 功能完全不回归
- 弹窗 UI 可切换但不影响已有功能

## 阶段1：前端状态模型与弹窗重构

### 目标

把当前文件夹弹窗从“单一逐拼图列表”升级为“子模式容器”。

### 重点文件

- `desktop/renderer/puzzle/index.js`
- `desktop/renderer/index.html`
- `desktop/renderer/puzzle.css`

### 核心任务

1. 重构 `openFolderModal()`
   - 从只克隆 `tempFolderBindings`
   - 变成构造完整 `tempMultiFolderDraft`

2. 拆分弹窗渲染函数
   建议从当前 `renderFolderModalList()` 拆成：

- `renderFolderModal()`
- `renderPerPuzzleFolderPanel()`
- `renderSubfolderBatchPanel()`

3. 新增子模式切换处理
   建议新增：

- `setFolderModalSubMode(subMode)`
- `syncFolderModalSubModeUI()`

4. 改造确认逻辑
   当前 `confirmFolderBindings()` 只写回 `folderBindings`
   后续要改成：

- 根据当前草稿整体写回多文件夹正式状态

### 风险点

- 弹窗重构最容易带来现有逐拼图模式回归
- 建议先保证 `per-puzzle-folder` 页面和行为 1:1 不变，再挂新面板

### 验收

- 弹窗内两个子模式都能切换
- `per-puzzle-folder` 原有选择/清除/确认/取消行为不变
- 取消不会污染正式状态

## 阶段2：子文件夹扫描与左侧图片列表

### 目标

先打通“选父目录 -> 扫描子文件夹 -> 弹窗显示 -> 左侧列表显示”，但暂不接入生成。

### 重点文件

- `desktop/preload.js`
- `desktop/main.js`
- `desktop/renderer/puzzle/index.js`

### 核心任务

1. 新增 preload API

```javascript
scanPuzzleSubfolderGroups: (payload) => ipcRenderer.invoke("puzzle:scanSubfolderGroups", payload)
```

2. 新增主进程 IPC

- `puzzle:scanSubfolderGroups`

3. 扫描逻辑实现

- 父目录第一层扫描子文件夹
- 子文件夹第一层扫描图片
- 使用自然排序

4. 前端接入子文件夹模式的“选择文件夹”

- 用户再次点击 `选择文件夹` 即视为重新扫描
- 不单独提供 `重新扫描` 按钮

5. 改造 `updateImageList()`
   新增第三路：

- `multi-folder + subfolder-batch`

### 关键建议

不要在这个阶段提前接任务引擎，否则问题来源会混在一起。

### 验收

- 子文件夹模式可选择父目录
- 弹窗显示 `X个子文件夹，共Y张`
- 左侧图片列表按子文件夹分组显示
- 空子文件夹、无子文件夹、路径不可访问三种状态可区分

## 阶段3：任务引擎与预计生成数

### 目标

让子文件夹模式的预计生成数与真实任务构建一致。

### 重点文件

- `desktop/renderer/puzzle/generation-engine.js`
- `desktop/renderer/puzzle/index.js`

### 核心任务

1. 扩展 `buildTaskQueue()` 参数
2. 新增 `buildSubfolderBatchQueue()`
3. 复用 `buildSingleQueue()`
4. 给任务增加来源元数据：

- `sourceGroupName`
- `sourceGroupPath`

5. 调整 `calculateEstimateCount()`
6. 调整 `handlePreview()` 与 `handleGenerate()` 的任务调用参数

### 关键实现原则

子文件夹模式严禁单独硬写简化公式，必须走真实任务构建。

### 风险点

- `singleFirstPuzzleOnce` 在当前 UI 中只对 `single` 直接可见
- 本阶段需要同步调整显示逻辑，否则产品行为和任务行为不一致

### 验收

- 子文件夹模式预计生成数正确
- 预览顺序与预期一致
- `拼图1作为封面` 在子文件夹模式下生效

## 阶段4：主进程导出链路

### 目标

让子文件夹模式的输出结构、目录命名和编号规则全部落地。

### 重点文件

- `desktop/renderer/puzzle/index.js`
- `desktop/main.js`

### 核心任务

1. 前端生成 payload 增加：

- `multiFolderSubMode`

2. 主进程识别：

- `generationMode === "multi-folder"`
- `multiFolderSubMode === "subfolder-batch"`

3. 调整导出目录选择逻辑

当前：

- 按拼图页目录

目标：

- 子文件夹模式下按 `sourceGroupName` 目录

4. 调整计数器逻辑

当前：

- `puzzleCountMap`

目标：

- 子文件夹模式下按 `sourceGroupName` 独立累计

### 风险点

- 这里最容易误伤现有 `per-puzzle-folder`
- 必须明确分支，不允许改成共享一套弱判断逻辑

### 验收

- 子文件夹模式勾选输出到子文件夹时按输入子文件夹输出
- 子文件夹模式不勾选时全局平铺连续编号
- 逐个指定拼图模式现有输出规则不回归

### 验收

## 八、风险清单

## 8.1 高风险

### 风险1：把子文件夹模式硬塞进 `folderBindings`

后果：

- 状态语义混乱
- 列表渲染和导出逻辑越来越难维护

控制方式：

- 使用独立 `multiFolderConfig.subfolderBatch`

### 风险2：预计生成数与真实导出不一致

后果：

- 用户直接感知错误

控制方式：

- 统一通过任务队列长度计算

### 风险3：误伤现有逐拼图导出规则

后果：

- 已有功能回归

控制方式：

- 主进程导出必须按子模式显式分支

## 8.2 中风险

### 风险4：模板工作区恢复异常

控制方式：

- 先兼容旧数据
- 所有新增字段提供 normalize

### 风险5：弹窗重构导致取消/确认边界失效

控制方式：

- 使用单独草稿对象
- 不直接操作正式状态

## 十、最终执行建议

本项目最合理的推进方式是：

1. 先完成阶段0到阶段2，让 UI、状态、扫描结果可见
2. 再进入阶段3和阶段4，把队列与导出打通
3. 最后统一做阶段5，把持久化与模板工作区收口

不建议直接跨阶段混改。

最推荐的首个开发提交范围是：

- 新增 `multiFolderConfig`
- 弹窗子模式骨架
- 新增 `puzzle:scanSubfolderGroups`
- 左侧图片列表第三种展示

这个阶段一旦稳定，后续任务引擎与导出改造会顺很多。
