# 百变拼图导出报错 `Illegal byte sequence` — P0-P2 开发规划

> 日期：2026-02-24  
> 状态：规划完成，待实施  
> 约束：本轮仅做定位与规划，不直接改业务代码

---

## 一、问题定位结论（基于真实数据）

### 1.1 真实数据路径

- 模板与素材目录：`C:\Users\Administrator\AppData\Roaming\scene-image-tool-desktop\PPT-Stitcher`
- 模板文件：`templates.json`
- 贴图目录：`stickers/`
- 背景目录：`backgrounds/`

### 1.2 样本对比（你给出的 D / E 模板）

- `D教案`：存在图片元素 `images[0]`
  - `imagePath: stickers/1771922460488_未命名(5)(10).png`
  - 该文件真实存在于 `stickers/`
- `E课件`：`images` 为空（无贴图元素）

### 1.3 现象与根因

- 现象：加图片元素后导出容易报 `Illegal byte sequence`，删掉图片元素后可导出。
- 根因（已确认方向）：导出链路里，图片元素解码在某些文件名/编码场景下失败，属于解码兼容问题，不是模板路径是否存在的问题，也不是“仅透明 PNG”问题。
- 结论：问题主要集中在“图片元素层（element layer）”的解码与异常上抛阶段。

### 1.4 当前仓库状态（已存在的未提交改动）

`desktop/main.js` 已经有一部分 P0 方向改造（未提交）：

1. 新增 `loadCanvasImageWithFallback(...)`（优先 Buffer 解码 + 归一化兜底）
2. `createElementLayerBuffer(...)` 改为读取文件 Buffer 后再解码
3. `createSlotImage(...)` 改为基于 Buffer + `sharp(..., { failOn: "none" })`
4. 背景图处理改为 Buffer 输入
5. 增加 `Illegal byte sequence` 的错误翻译

说明：上述改动方向正确，但还不构成“完整闭环”。下文给出完整 P0-P2。

## 二、目标与边界

### 2.1 目标

1. 百变拼图导出在中文/特殊字符图片名场景稳定可用
2. 错误信息可定位到阶段和文件，不再只给泛化报错
3. 支持批量导出时“可部分成功”，并返回失败清单

### 2.2 非目标

1. 本次不调整模板编辑交互逻辑
2. 不做渲染效果层面的视觉改动
3. 不引入新的导出格式（仍以 PNG 为主）

---

## 三、P0（阻断问题修复，必须先上线）

目标：先彻底解决“导出直接失败”的主问题，保障可导出。

### 3.1 后端导出链路补齐（主进程）

文件：`desktop/main.js`

1. 统一“图片输入只走 Buffer”策略  
   - 作用范围：背景、坑位素材、图片元素
   - 不再在关键链路依赖路径直读解码
2. 对 `createElementLayerBuffer(...)` 增加阶段化错误上下文  
   - 抛错包含：`stage=element_decode`、`file=basename`、`imagePath`
3. 对 `puzzle:generate` 增加阶段化错误包装  
   - 至少区分：`background_decode` / `slot_decode` / `element_decode` / `composite` / `output_write`
4. 修正 `translateSharpError(...)` 文案  
   - 去掉“透明 PNG 常见”这种误导性表述
   - 改为“图片解码或编码异常（含文件名编码/文件损坏/格式兼容）”

### 3.2 前端错误展示补齐（渲染进程）

文件：`desktop/renderer/puzzle/index.js`

1. 解析后端返回的结构化错误字段（stage/file/message）
2. 导出失败 toast 显示“阶段 + 文件名（若有）”
3. 状态栏同步写入同样信息，便于截图反馈

### 3.3 P0 验收标准

1. 用真实模板 `D教案` 导出成功（至少 1x、2x 各一次）
2. `E课件` 回归不受影响
3. `stickers/` 中含中文、括号、空格文件名均可导出
4. 故意放入异常图片时，错误提示中可看到阶段与文件名

## 四、P1（稳定性增强）

目标：即使个别素材失败，也尽量不中断整批任务。

### 4.1 局部失败不拖垮全量任务

文件：`desktop/main.js`

1. `puzzle:generate` 从“整批 try/catch”改为“单任务 try/catch + 汇总”
2. 输出结构升级：
   - `ok`
   - `count`（成功数）
   - `failed`（失败项数组：index/puzzleName/stage/file/error）
3. 新增策略参数（可选）：
   - `continueOnError: true`（默认 true）

### 4.2 前端结果呈现升级

文件：`desktop/renderer/puzzle/index.js`

1. 当 `failed.length > 0` 且 `count > 0`：
   - 提示“部分成功”
   - 弹出失败摘要（前 N 条）
2. 提供“复制失败列表”到剪贴板（便于反馈）

### 4.3 P1 验收标准

1. 100 张任务里 1 张异常时，其余 99 张照常生成
2. 前端明确展示成功/失败数量与失败文件
3. 错误摘要可直接用于复盘定位

## 五、P2（工程化与预防）

目标：降低后续同类问题出现概率，形成可持续验证机制。

### 5.1 文件命名与入库规范

文件：`desktop/main.js`（`puzzle:copySticker` / `puzzle:copyBackground`）

1. 入库时生成稳定安全文件名（时间戳 + 短 hash + 原扩展名）
2. 原文件名仅作为展示字段保存，不参与底层读写
3. 降低复杂字符名对底层库的兼容风险

### 5.2 回归脚本与测试资产

文件：建议新增 `desktop/scripts/puzzle-export-smoke.js`

1. 自动跑最小复现矩阵（含中文名、空格、括号、超大图）
2. 输出每个样例的 `pass/fail + stage`
3. 发布前作为手工回归脚本标准步骤

### 5.3 文档与支持流程

文件：`docs/用户说明书.md`（补充）

1. 增加“导出失败排查”章节
2. 失败反馈模板统一化（带 stage/file/version）

### 5.4 P2 验收标准

1. 新增脚本可一键跑完核心样例
2. 发布前回归有固定流程和固定输出
3. 同类问题可在提测阶段提前暴露

## 七、风险与回滚

### 7.1 风险

1. 错误结构升级后，前端若未兼容可能出现提示缺失
2. 部分成功逻辑若处理不当可能导致“看似成功但有漏图”
3. 文件重命名策略变更需注意历史模板兼容

### 7.2 回滚策略

1. P0 回滚：保留 Buffer 解码路径，关闭结构化错误扩展
2. P1 回滚：关闭 `continueOnError`，恢复“遇错终止”
3. P2 回滚：命名策略加开关，必要时回退到旧命名
