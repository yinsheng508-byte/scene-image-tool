# 文档导出性能优化 — 完整改造规划

> 文档版本：2026-03-13
> 基于 `desktop/main.js` 源码精确审查 + Codex / Gemini 方案综合梳理
> **注意：当前架构为 LibreOffice 链路**，旧文档（`文档导出优化方案.md`、`PPT导出卡死与速度优化.md`）描述的 Office COM / PowerShell 链路已被替换，不再适用。

> 本次增量复核（2026-03-13 晚）关键结论：
> 1) `batchConvertToPdf()` 在 `desktop/main.js` 中当前仅有定义、无调用，`loSpeedMode/boost` 相关逻辑属于**预留代码**，不在主链路生效。
> 2) `officeTimeoutMs / pptPerFileTimeoutMs` 当前未透传到 `runPptToPdfWithRetry(policy.timeoutMs)`，PPT 实际仍主要使用 `SCENE_OFFICE_TIMEOUT_MS`（默认 180s）作为基础超时。
> 3) 若直接按旧文档改 `boost` 或 `pptOfficeConcurrency`，收益会偏低；优先应先打通“参数真实生效链路”。

## 二、性能瓶颈精确分析

### 2.1 瓶颈 1：LibreOffice 冷启动（最大瓶颈，无法完全消除）

**位置**：`runLibreOfficeToPdfOnce()` [main.js:3663]

每次调用都会：
1. `mkdtemp` 创建新 profile 目录（~100ms，低配磁盘更慢）
2. spawn 新 `soffice.exe` 进程，带 7 个参数
3. LO 冷启动：低配机 15-30 秒，中配 8-12 秒，高配 5-8 秒
4. 文件解析转换：依文件大小，大 PPT 100MB+ 可达 2-5 分钟
5. 进程退出 + profile 目录清理

**结论**：10MB PPT 在低配机上约需 **45-80 秒**，100MB PPT 可达 **3-8 分钟**。

### 2.2 瓶颈 2：PDF→PNG 渲染阶段并发不足

**位置**：`convertPdfBufferToImages()` [main.js:4344]

```javascript
// 当前：批量并发渲染（已有基础，但上限保守）
for (let index = 0; index < limit; index += pageConcurrency) {
  const batch = [];
  for (let offset = 0; offset < pageConcurrency && ...; offset += 1) {
    batch.push(renderPage(index + offset));
  }
  await Promise.all(batch);
}
```

`pageConcurrency` 最大值 = 2（高配机也只有 2），8核以上机器浪费了约 75% 的 CPU 渲染能力。

每页峰值内存：4000×3000 像素 ≈ 48MB RGBA，60MP 上限 ≈ 240MB RGBA。并发 4 页 = ~200-400MB，高配机完全可承受。

### 2.3 瓶颈 3：进度上报频率过高（低配机卡 UI）

**位置**：`createRenderReporters()` [main.js:4844]

每页渲染完成都调用 `sendProgress()`，触发 IPC 消息 → 渲染进程 DOM 更新。低配机单文件 30 页 PPT = 30 次 IPC + DOM 更新，在 PDF 渲染高 CPU 负载时会加剧主进程卡顿感。

### 2.4 瓶颈 4：关键调优参数未真正打通（高优先级）

**定位链路（实测代码）**：

1. `convert:documents` 组装 `options.officeTimeoutMs / options.pptPerFileTimeoutMs`（main.js:5099, 5115）
2. `convertPptToImages()` 调 `convertPptSourceToPdf(..., options)`（main.js:4621）
3. `runPptToPdfWithRetry(policy)` 内实际读取的是 `policy.timeoutMs`（main.js:4469）
4. 当前未把 `officeTimeoutMs/pptPerFileTimeoutMs` 映射到 `policy.timeoutMs`

**直接结果**：

- PPT 超时大多仍回落到 `SCENE_OFFICE_TIMEOUT_MS`（默认 180000）
- 文档中的档位超时策略（例如 low=120000）当前不能稳定生效
- 调参看似成功但实际无变化，造成“优化错觉”

```javascript
// 当前 runPptToPdfWithRetry
const baseTimeoutMs = parsePositiveInt(
  policy.timeoutMs,
  parsePositiveInt(process.env.SCENE_OFFICE_TIMEOUT_MS, DEFAULT_OFFICE_TIMEOUT_MS)
);
```

**修复优先级**：P0（先打通，再谈调参）。

### 2.5 瓶颈 5：useSubfolder=false 时文件并发强制为 1

**位置**：main.js:5073

```javascript
const fileConcurrency = useSubfolder ? concurrency.fileConcurrency : 1;
```

不勾选"输出到子文件夹"时，文件并发被锁为 1，即使高配机也无法利用多核。

### 2.6 瓶颈 6：并发命名前缀存在竞态窗口

**位置**：`resolveOutputNamePrefix()` [main.js:3933]

当前前缀冲突检测基于目录快照（`readdir`）+ 本地判断；并发任务在同目录同基名时，可能同时选中同一前缀，存在覆盖风险。该问题在“放开 useSubfolder=false 并发”后风险更高。

## 三、分层改造策略

### 3.1 机器档位重新定义

| 档位 | 判定条件 | 目标 |
|------|----------|------|
| **low（低配）** | CPU ≤ 4核 **或** 可用内存 < 3GB | 稳定不崩，不卡死 |
| **mid（中配）** | CPU 5-7核 且 可用内存 3-8GB | 均衡，适度提速 |
| **high（高配）** | CPU ≥ 8核 且 可用内存 ≥ 8GB | 榨干性能，吞吐优先 |
| **ultra（极配）** | CPU ≥ 12核 且 可用内存 ≥ 16GB | 最大并发，流水线优化 |

### 3.2 各档位参数矩阵

| 参数 | low | mid | high | ultra |
|------|-----|-----|------|-------|
| `smallQueueConcurrency`（主生效） | 1 | 2 | 3 | 4 |
| `pageConcurrency`（主生效） | 1 | 2 | 4 | 6 |
| `largeFileThresholdMb`（主生效） | 60 | 80 | 100 | 120 |
| `largeFileMaxAttempts`（主生效） | 2 | 2 | 2 | 2 |
| `pptRetryCount`（主生效） | 0~1 | 1 | 1 | 1 |
| `officeConcurrency`（当前间接） | 1 | 2 | 2 | 3 |
| `degradeFailStreak`（当前间接） | 1 | 2 | 3 | 3 |
| `recoverSuccessWindow`（当前间接） | 4 | 6 | 8 | 10 |
| `officeTimeoutMs` / `pptPerFileTimeoutMs` | 120000 | 180000 | 180000 | 180000 |

> 说明：
> 1) `smallQueueConcurrency` 才是当前主链路中的“实际 LO 并发上限”（任务级并发）。
> 2) `officeConcurrency` 目前主要影响自适应控制器目标值，且受 `smallQueueConcurrency` 上限约束。
> 3) `officeTimeoutMs/pptPerFileTimeoutMs` 需先完成“参数透传修复”后才会真正按档位生效。

### 3.3 低配机专项策略

**问题核心**：低配机瓶颈不是并发不够，而是单次 LO 启动就把 CPU 吃满，并发反而互相抢占导致都更慢。

专项措施：
1. **强制串行任务**：`smallQueueConcurrency=1`（当前最直接有效）
2. **大文件阈值调低到 60MB**：更多文件走 largeQueue（有重试保护）
3. **更短的超时感知**：先修复超时参数透传，再将 low 档基础超时设为 120s
4. **进度上报降频**：每 3 页上报一次（而不是每页），减少主进程 IPC 压力
5. **scale≥2 时强制 pageConcurrency=1**：高分辨率渲染内存占用大，低配机串行避免 OOM

### 3.4 高配机专项策略

**问题核心**：高配机当前参数与中配机几乎相同，大量 CPU 核心在 PDF 渲染阶段闲置。

专项措施：
1. **pageConcurrency 提升到 4-6**：8核机器可轻松支持 4 页并发渲染
2. **smallQueueConcurrency 提升到 3-4**：多文件批量时更快推进
3. **放开非子目录模式并发（需配套防重名竞态）**
4. **将“每页日志+每页 IPC”降频或抽样**，降低主线程负担
5. **ultra 档新增**：12核/16GB+ 机器进一步放开 pageConcurrency=6, smallQueueConcurrency=4

## 四、具体改动方案

### 改动 A：机器分层函数重构

**文件**：`desktop/main.js`

**涉及函数**（3 个）：
- `getMaxConcurrency()` [4004]
- `getSmallQueueConcurrencyCap()` [4013]
- `getPptMachinePolicyBaseline()` [4034]

**改动思路**：统一用一个 `getMachineTier()` 函数判断档位，其他函数查表返回。

```javascript
// 新增：统一档位判断
function getMachineTier() {
  const cpuCount = Array.isArray(os.cpus()) ? os.cpus().length : 1;
  const freeMemMB = os.freemem() / (1024 * 1024);
  if (cpuCount >= 12 && freeMemMB >= 12000) return "ultra";
  if (cpuCount >= 8 && freeMemMB >= 8000) return "high";
  if (cpuCount >= 5 && freeMemMB >= 3000) return "mid";
  return "low";
}

// 改动：getMaxConcurrency() 增加 high/ultra 档
function getMaxConcurrency() {
  const tier = getMachineTier();
  if (tier === "ultra") return { pageConcurrency: 6, fileConcurrency: 3 };
  if (tier === "high")  return { pageConcurrency: 4, fileConcurrency: 2 };
  if (tier === "mid")   return { pageConcurrency: 2, fileConcurrency: 1 };
  return { pageConcurrency: 1, fileConcurrency: 1 };
}

// 改动：getSmallQueueConcurrencyCap() 增加 high/ultra 档
function getSmallQueueConcurrencyCap() {
  const tier = getMachineTier();
  if (tier === "ultra") return 4;
  if (tier === "high")  return 3;
  if (tier === "mid")   return 2;
  return 1;
}

// 改动：getPptMachinePolicyBaseline() 增加 ultra 档，high 档提升参数
function getPptMachinePolicyBaseline() {
  const tier = getMachineTier();
  if (tier === "ultra") {
    return { tier: "ultra", officeConcurrency: 3, perFileTimeoutMs: 180000, batchComRestartSize: 10 };
  }
  if (tier === "high") {
    return { tier: "high", officeConcurrency: 2, perFileTimeoutMs: 180000, batchComRestartSize: 8 };
  }
  if (tier === "mid") {
    return { tier: "mid", officeConcurrency: 2, perFileTimeoutMs: 180000, batchComRestartSize: 5 };
  }
  // low
  return { tier: "low", officeConcurrency: 1, perFileTimeoutMs: 120000, batchComRestartSize: 3 };
}
```

**风险评估**：低。只改参数返回值，不改调用链。可通过 env 变量覆盖验证。

### 改动 D：进度上报降频（低配机减少 IPC 压力）

**文件**：`desktop/main.js`

## 五、改动优先级与实施顺序

### 优先级矩阵

| 改动 | 优先级 | 受益方 | 改动量 | 风险 | 说明 |
|------|--------|--------|--------|------|------|
| **A：机器分层重构** | **P0** | 高配机**立刻提速** + 低配机更稳 | ~40 行 | 低 | 核心改动，其他改动依赖它 |
| **B：超时参数透传修复** | **P0** | 全档位 | ~10 行 | 低 | 先保证参数真实生效 |
| **C：策略字段对齐** | **P0** | 全档位 | ~10-20 行 | 低-中 | 降低“配置无效”风险 |
| **D：进度上报降频** | **P0** | 低配机 UI 不卡 | ~10 行 | 低 | 用户体验直接受益 |
| **E：大文件阈值按档位** | **P1** | 低配机稳定性 | ~10 行 | 低 | 改动 A 完成后 5 分钟可做 |
| **F：useSubfolder=false 并发** | **P2** | 高配机不勾子文件夹时提速 | ~5 行 | 中 | 需配套改动 G |
| **G：resolveOutputNamePrefix 竞态安全** | **P2** | 并发安全前提 | ~20 行 | 低 | 改动 F 的前提 |

### 建议实施顺序

```
第一批（P0，立即做，1天内完成）：
  改动 B → 改动 C → 改动 A → 改动 D

第二批（P1，验证第一批后做）：
  改动 E（按档位调阈值，压低低配崩溃率）

第三批（P2，稳定后可选）：
  改动 G（前置）→ 改动 F
```

## 六、待深入讨论的问题

### 6.1 Profile 预热/复用（Codex/Gemini 提到）

**方案描述**：不每次销毁 profile，而是复用同一目录，节省 ~1-3 秒启动时间。

**当前实现**：`runLibreOfficeToPdfOnce` 每次 `mkdtemp` 创建新 profile，任务结束后 `rm` 删除。

**可行性评估**：
- `isolated` 模式（当前默认）：每文件独立进程，复用 profile 可能导致上一次 LO 未完全清理时新实例读到旧 profile 状态
- LO 在 Windows 上有 profile 锁文件（`registrymodifications.xcu`），并发复用同一 profile 会直接报 `LO_PROFILE_LOCK`
- **可行方案**：维护一个小的"清洁 profile 模板目录"，每次 `copy` 模板而不是从零初始化
- **前提**：测量 LO profile 初始化占总耗时的比例（需要实测，怀疑在低配机上 profile 创建占 1-2 秒）

**结论**：需要实测数据后决策，暂不纳入本批改造。

### 6.2 LO 常驻进程（Daemon 模式）

**方案描述**：在 Electron 启动时预启动一个 LO 服务进程，用 `--accept` 或 `unoserver` 保持热进程，消除冷启动。

**可行性评估**：
- LO 官方 `unoserver` 在 Windows 标注 `untested`
- LO `--headless --accept` 模式在 Windows 上有已知稳定性问题
- 每文件操作需要通过 UNO API，需要大改转换逻辑
- 对低配机额外占用 300-500MB 内存

**结论**：中期目标，不在本次改造范围。

### 6.3 流水线并行（中期增强项）

**方案描述**：文件 A 在 LO 转换 PDF 时，文件 B 已经完成 LO 转换，立即开始 PDF 渲染，两阶段流水线重叠。

**当前架构**：`convertPptToImages()` 内部串行：先 LO 转换 → 再 PDFium 渲染，不会跨文件重叠。

**实现路径**：需要将 "LO 批量转换" 和 "PDF 渲染" 分离为独立阶段，转换完一个文件立即 emit 给渲染阶段。

**改动量**：较大，需要重构 `processTaskFromQueue` 的调度逻辑，引入流水线队列。

**结论**：高配机有意义，但改动量较大，建议放在 P2 批次后评估。

### 6.4 预留代码处置：`batchConvertToPdf` / `loSpeedMode`

现状：`batchConvertToPdf` 当前不在 `convert:documents` 主链路；`loSpeedMode` 主要体现在诊断日志。

建议二选一，避免长期灰区：
1. **接入方案**：把 smallQueue 中 Office 文件分支切到 `batchConvertToPdf`，并补齐 20 文件并发 + 大文件 + pageLimit 回归用例。
2. **收敛方案**：短期内不接入，删除/隐藏 `boost` 文案，避免用户误以为可提速。

### 6.5 前端 UI 进度条分阶段显示

**当前**：进度条显示 `0/N` 直到第一个文件完成，用户看到的是"卡住"。

**改善方案**：区分以下 phase 的视觉反馈
- `PPT 转 PDF（LO 阶段）`：显示"正在解析文档..."
- `PDF 渲染（PDFium 阶段）`：显示进度百分比
- 心跳间隔 10s 的日志已存在，但没有在 UI 上体现 LO 处理时长

**具体改动**：[renderer.js:2207] 的 `data.phase === "page"` 处增加阶段标签，并在 LO 超时前每 15s 在 `convertStatus` 里刷新已用时间。

## 七、验收标准

### 7.1 低配机验收（≤4核 / <3GB 可用内存）

- [ ] 20MB PPT 文件单次导出不超时（< 180s）
- [ ] 5个 20MB PPT 批量导出，不因 OOM 或 LO 崩溃导致全部失败
- [ ] UI 不出现长时间"卡住不动"（进度条有更新）
- [ ] 日志中 tier 字段显示 `"low"`

### 7.2 高配机验收（≥8核 / ≥8GB 可用内存）

- [ ] `smallQueueConcurrency` 在高配机可稳定跑到 3（或更高目标值）
- [ ] 10 个 10 页 PPT 批量导出，总时间比改前缩短 ≥ 30%
- [ ] `pageConcurrency` 日志显示 4（而不是 2）
- [ ] 日志中 tier 字段显示 `"high"` 或 `"ultra"`

### 7.3 通用验收

- [ ] 改动 A 前后对比：`导出诊断` 日志中 `tier=` 字段已更新
- [ ] 大文件（>60MB）走 largeQueue 串行路径，不并发
- [ ] PPT 路径日志中 `pptPerFileTimeoutMs` 与实际超时生效一致（通过故障注入或超大文件验证）
- [ ] 取消功能正常，LO 进程被正确终止

## 八、环境变量速查（调试用）

可通过以下环境变量覆盖参数（基于当前代码已实现项）：

```bash
# PPT/队列策略（已生效）
SCENE_PPT_OFFICE_CONCURRENCY=2        # 自适应控制器基线（受 smallQueue 上限约束）
SCENE_PPT_ADAPTIVE_ENABLE=false       # 关闭自适应降级
SCENE_PPT_RETRY_COUNT=1               # PPT 转 PDF 失败重试次数

# 转换超时（注意：需完成“改动B 参数透传修复”后，pptPerFile 才完全按预期生效）
SCENE_OFFICE_TIMEOUT_MS=90000         # 基础超时 90s（当前 PPT 主生效基础）
SCENE_PPT_PER_FILE_TIMEOUT_MS=60000   # PPT 每文件基础超时
SCENE_WORD_TIMEOUT_MS=120000          # Word 每文件基础超时

# 文件分类
SCENE_LO_LARGE_FILE_THRESHOLD_MB=60   # 大文件阈值改为 60MB
SCENE_LO_LARGE_FILE_MAX_ATTEMPTS=2    # 大文件尝试次数（首次+重试）

# 运行时
SCENE_LO_RUNTIME_MODE=auto            # auto / embedded / system
SCENE_LO_PERF_TUNING=true             # 性能策略总开关（false 回退旧策略）

# 预留项（当前主链路影响有限）
SCENE_LO_SPEED_MODE=boost             # 当前主要用于诊断字段
SCENE_PPT_FORCE_MODE=isolated         # 当前无实质分支切换
```

`smallQueueConcurrency` 当前来自 `convert:documents` payload（非环境变量），压测时请通过请求参数传入。

### 10.2 M0 基线固化（必须先做）

目标：
1. 固化“改前数据”，避免后续优化无对照。

开发任务：
1. 固定测试集：`332MB PPT`、`20 文件混合批量`、`pageLimit=3`、`scale=1x/3x`、`useSubfolder=true/false`。
2. 记录指标：总耗时、PPT->PDF耗时、PDF->PNG耗时、成功率、错误码分布、峰值CPU/内存。
3. 固化导出诊断日志字段，确保每次测试都可比对。
4. 使用 `npm --prefix desktop run perf:baseline -- --input <report-json...> --out baseline-summary.json` 聚合基线报告。

验证任务：
1. 连续跑 3 轮，取中位数写入 baseline。

退出产物：
1. `baseline` 数据表（可放 `docs` 或测试报告 JSON）。

### 10.3 M1 参数生效修复（P0）

目标：
1. 先修“调参不生效”问题，再做性能调优。

开发任务：
1. 修复 `convertPptToImages -> convertPptSourceToPdf -> runPptToPdfWithRetry` 的 `timeoutMs` 透传。
2. 对齐策略字段语义：把当前未参与执行的字段标记为“诊断/预留”，避免误导。
3. 保持默认行为兼容，不改变已有导出结果格式。

验证任务：
1. 故障注入验证：缩短超时参数后，PPT 路径能按预期提前超时。
2. 日志校验：`pptPerFileTimeoutMs` 与实际行为一致。
3. 回归：Word/PPT/PDF 基础导出不回归。

退出条件：
1. `timeout` 调参可稳定生效。
2. 无新增高频失败码。

### 10.4 M2 并发分层提速（P0/P1）

目标：
1. 低配稳，高配快，策略简单可控。

开发任务：
1. 重构机器档位判定（low/mid/high/ultra），统一驱动 `pageConcurrency`、`smallQueueConcurrencyCap`、`policy baseline`。
2. 落地低配保护：`smallQueueConcurrency=1`、高分辨率降并发、大文件优先进 `largeQueue`。
3. 落地高配提速：提高 `pageConcurrency` 与 `smallQueueConcurrency` 上限。
4. 进度上报降频：低配按页抽样上报，减少 IPC/DOM 压力。

验证任务：
1. 低配场景：稳定性优先，确保不因并发上调导致失败率增加。
2. 高配场景：吞吐对比 baseline，目标总耗时下降 30%（批量场景）。
3. 大文件场景：`largeQueue` 串行+重试策略持续生效。

退出条件：
1. 性能目标达成或接近目标且稳定性无回退。
2. 关键指标可重复复现（至少 3 轮）。

### 10.5 M3 稳定性护栏（P2）

目标：
1. 解决并发下潜在覆盖写风险，安全放开非子目录并发。

开发任务：
1. 为 `resolveOutputNamePrefix` 增加批次内前缀分配表（内存态去重）。
2. 在 `useSubfolder=false` 场景按档位逐步放开 `fileConcurrency`。
3. 明确冲突与回退逻辑，保证不覆盖既有输出文件。

验证任务：
1. 同名文件、同目录、多并发混合压测。
2. 对比导出结果文件数量与命名唯一性。

退出条件：
1. 并发输出零覆盖、零丢图。

### 10.6 M4 灰度验收与发布收敛

目标：
1. 以最小风险发布，保留快速回退能力。

开发任务：
1. 增加灰度开关与默认值策略（优先 safe）。
2. 完成回归用例清单并执行全量验证。
3. 更新用户文档与运维排障文档（参数说明、错误码、推荐配置）。

验收任务：
1. 离线 Full 包验证。
2. 低配机长任务验证（2-3 分钟级 PPT 转换）。
3. 20 文件批量 + pageLimit + 3x 分辨率组合验证。

发布策略：
1. 先小流量灰度，再全量。
2. 观测窗口建议 3 天，重点看 `LO_TIMEOUT/LO_NON_ZERO_EXIT/LO_OUTPUT_MISSING`。

退出条件：
1. 达到功能正确性、稳定性、性能三项门槛。

### 10.7 阶段验收清单（统一）

1. 功能正确性：导出页数、命名、目录结构、pageLimit、3x 分辨率均符合预期。
