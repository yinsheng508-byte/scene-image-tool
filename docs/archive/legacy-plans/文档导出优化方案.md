## 二、问题一：命名不一致（`-1` vs `-1-1`）

### 2.1 现有命名机制

`getOutputFilePath()` (main.js:1538-1556) 采用 **4 级回退命名**：

```
useSubfolder=true 时:
  优先级1: {baseName}-{pageNumber}.png
  优先级2: {baseName}-{extSuffix}-{pageNumber}.png
  优先级3: {baseName}-{extSuffix}-{pageNumber}-{i}.png  (i=1..999)
  优先级4: {baseName}-{extSuffix}-{pageNumber}-{timestamp}.png

useSubfolder=false 时:
  优先级1: {baseName}-{extSuffix}-{pageNumber}.png
  优先级3: {baseName}-{extSuffix}-{pageNumber}-{i}.png  (i=1..999)
  优先级4: {baseName}-{extSuffix}-{pageNumber}-{timestamp}.png
```

页码来源 (main.js:1663):
```javascript
const pageNumber = page.number || index + 1;
```

`page.number` 是 PDFium 库返回的页码，通常从 1 开始。

### 2.2 根因分析

命名不一致的直接原因是 **按页检测冲突并逐页回退**，导致同一批次内不同页面命中不同级别的回退。

常见触发场景：
- **未勾选「输出到子文件夹」**：所有文件共用同一输出目录，历史文件极易冲突。
- **勾选子文件夹但重复导出同一文件**：子目录内存在旧图片。
- **文件名本身为数字或含 `-1`**：例如 `1.docx` 第1页输出为 `1-1.png`，视觉上容易与“冲突后缀”混淆（但这本身不是冲突）。

**核心问题：** 当前回退逻辑是“逐页判断”，不同页可能落到不同规则，导致同一批次命名不统一。

### 2.3 Codex 补充观点

> "如果文件名本身就是 `1.docx`，baseName=1，第一页会变成 `1-1.png`（baseName-页码），容易与冲突后缀混淆。"

这是一个有效的边界场景：当 baseName 本身含数字时，`-1` 后缀的语义模糊（是页码还是冲突序号？）。

### 2.4 修复方案

**方案 A：固定“文件级命名前缀”（推荐）**

**核心思路：** 在渲染前为每个文件 **只选一次** 命名前缀（prefix），之后所有页都用该前缀，避免逐页回退造成混乱。**不删除旧文件**，但确保同一批次内命名规则一致。

```javascript
async function resolveOutputNamePrefix(outputDir, baseName, extSuffix, useSubfolder) {
  let existing = [];
  try {
    existing = await fs.promises.readdir(outputDir);
  } catch {
    existing = [];
  }

  const hasPrefix = (prefix) =>
    existing.some((name) => name.startsWith(`${prefix}-`) && name.endsWith(".png"));

  if (useSubfolder) {
    if (!hasPrefix(baseName)) return baseName;
    const alt = `${baseName}-${extSuffix}`;
    if (!hasPrefix(alt)) return alt;
  } else {
    const base = `${baseName}-${extSuffix}`;
    if (!hasPrefix(base)) return base;
  }

  for (let i = 1; i <= 999; i += 1) {
    const candidate = `${baseName}-${extSuffix}-${i}`;
    if (!hasPrefix(candidate)) return candidate;
  }
  return `${baseName}-${extSuffix}-${Date.now()}`;
}
```

渲染时固定前缀：

```javascript
const namePrefix = await resolveOutputNamePrefix(outputDir, item.baseName, item.ext.slice(1), options.useSubfolder);
// 传入 options 给 convertPdfBufferToImages
const nextOptions = { ...options, namePrefix };
```

`getOutputFilePath()` 支持固定前缀：

```javascript
function getOutputFilePath(outputDir, baseName, extName, pageNumber, useSubfolder = true, namePrefix = null) {
  if (namePrefix) {
    return path.join(outputDir, `${namePrefix}-${pageNumber}.png`);
  }
  // 兼容旧逻辑（可逐步移除）
}
```

**优点：**
- 同一批次内命名规则一致（不会出现 `-1` vs `-1-1` 混用）
- 不删除历史文件，风险低
- 适用于 `useSubfolder=true/false`

**方案 B：固定 pageNumber 为 index + 1**

Codex 建议将 `page.number` 改为始终使用 `index + 1`：

```javascript
// 现有
const pageNumber = page.number || index + 1;
// 改为
const pageNumber = index + 1;
```

**评估：** 这只解决 `page.number` 可能不连续的极端情况，不解决“逐页回退”导致的命名混乱。**建议作为方案 A 的补充**。

**方案 C（可选）：覆盖式导出**

若业务允许覆盖旧结果，可新增“覆盖导出”开关（默认关闭），开启后对 **子目录** 执行清空。此方案可保证永远使用 `baseName-pageNumber.png`，但会删除历史结果。

**最终建议：方案 A + 方案 B。**

## 三、问题二：批量 PowerShell 脚本（COM 复用）

### 3.1 当前问题

```
10 个 Word 文件的处理时间线:

文件1: [启动Word 3s][打开+转PDF 2s][关闭Word 1s]
文件2: [启动Word 3s][打开+转PDF 2s][关闭Word 1s]
...
文件10:[启动Word 3s][打开+转PDF 2s][关闭Word 1s]

总 COM 开销: 10 × (3+1) = 40s
总转换时间:   10 × 2 = 20s
合计: ~60s
```

**三方共识：** 每个文件启动/销毁一次 COM 对象是最大的单项瓶颈。Word COM 启动约 2-4 秒，PPT COM 启动约 3-5 秒。

### 3.2 批量脚本方案

```json
  { "input": "D:\\docs\\file2.docx", "output": "D:\\temp\\file2.pdf" }
]
```

#### 新增脚本: `word-batch-to-pdf.ps1`

```powershell
param(
    [Parameter(Mandatory = $true)][string]$TaskFile
)

$word = $null
$results = @()

try {
    $tasks = Get-Content $TaskFile -Raw -Encoding UTF8 | ConvertFrom-Json
    if ($tasks -isnot [System.Collections.IList]) {
        $tasks = @($tasks)
    }
    if ($tasks -isnot [System.Collections.IList]) {
        $tasks = @($tasks)
    }

    if ($tasks.Count -eq 0) {
        Write-Output "[]"
        exit 0
    }

    $word = New-Object -ComObject Word.Application   # ← 只启动一次
    $word.Visible = $false
    $word.DisplayAlerts = 0

    foreach ($task in $tasks) {
        $doc = $null
        try {
            $doc = $word.Documents.Open($task.input, $false, $true)
            $doc.ExportAsFixedFormat($task.output, 17, $false, 0)
            $results += @{ id = $task.id; input = $task.input; ok = $true; error = "" }
        }
        catch {
            $results += @{ id = $task.id; input = $task.input; ok = $false; error = $_.Exception.Message }
        }
        finally {
            if ($doc -ne $null) {
                try { $doc.Close($false) } catch { }
            }
        }
    }
}
catch {
    Write-Error $_.Exception.Message
    exit 1
}
finally {
    if ($word -ne $null) {
        try { $word.Quit() } catch { }
        [System.Runtime.Interopservices.Marshal]::ReleaseComObject($word) | Out-Null
    }
    [System.GC]::Collect()
    [System.GC]::WaitForPendingFinalizers()
}

# 输出 JSON 结果到 stdout
$results | ConvertTo-Json -Compress
```

### 3.3 main.js 改造方案

#### 新增函数: `batchConvertToPdf()`

```javascript
/**
 * 批量将 Word 或 PPT 转为 PDF
 * @param {'word'|'ppt'} type - 文档类型
 * @param {Array<{sourcePath: string, pdfPath: string, item: object}>} tasks - 任务列表
 * @returns {Array<{sourcePath: string, pdfPath: string, ok: boolean, error?: string}>}
 */
async function batchConvertToPdf(type, tasks) {
  if (tasks.length === 0) return [];

  const scriptName = type === 'word' ? 'word-batch-to-pdf.ps1' : 'ppt-batch-to-pdf.ps1';

  // 1. 处理中文路径 — 批量创建安全路径
  const tempDir = await fs.promises.mkdtemp(path.join(os.tmpdir(), `scene-batch-${type}-`));
  const safeDir = path.join(tempDir, 'safe');
  const cleanups = [];

  const taskList = [];
  for (let i = 0; i < tasks.length; i++) {
    const t = tasks[i];
    const safeInput = await ensureSafeInputPath(t.sourcePath, path.join(safeDir, String(i)), t.item.ext);
    if (safeInput.cleanup) cleanups.push(safeInput.cleanup);
    taskList.push({ id: i, input: safeInput.path, output: t.pdfPath });
  }

  // 2. 写入 JSON 任务文件
  const taskFilePath = path.join(tempDir, 'tasks.json');
  await fs.promises.writeFile(taskFilePath, JSON.stringify(taskList), 'utf-8');

  try {
    // 3. 调用批量脚本
    const stdout = await runPowerShellWithOutput(scriptName, [taskFilePath]);

    // 4. 解析结果
    let results;
    try {
      const cleaned = stdout.replace(/^\uFEFF/, "");
      results = JSON.parse(cleaned);
    } catch {
      // 解析失败，全部标记为失败
      return tasks.map((t) => ({ ...t, ok: false, error: "PowerShell 输出解析失败" }));
    }

    const list = Array.isArray(results) ? results : [results];
    const resultMap = new Map(list.map((r) => [r.id, r]));

    // 5. 映射回原始任务（用 id 保证稳定）
    return tasks.map((t, i) => {
      const r = resultMap.get(i);
      return {
        ...t,
        ok: r?.ok ?? false,
        error: r?.error || ""
      };
    });
  } finally {
    // 6. 清理临时目录
    for (const cleanup of cleanups) {
      try { await cleanup(); } catch { }
    }
    try {
      await fs.promises.rm(tempDir, { recursive: true, force: true });
    } catch { }
  }
}
```

#### 新增函数: `runPowerShellWithOutput()`

在现有 `runPowerShell()` (L1487) 基础上增加 stdout 捕获：

```javascript
function runPowerShellWithOutput(scriptName, args) {
  const scriptPath = path.join(getScriptsPath(), scriptName);
  if (!fs.existsSync(scriptPath)) {
    return Promise.reject(new Error(`脚本不存在: ${scriptPath}`));
  }
  return new Promise((resolve, reject) => {
    const ps = spawn(getPowerShellExe(), [
      "-NoProfile",
      "-ExecutionPolicy",
      "Bypass",
      "-File",
      scriptPath,
      ...args
    ], {
      windowsHide: true
    });

    let stdout = "";
    let stderr = "";
    ps.stdout.on("data", (data) => { stdout += data.toString(); });
    ps.stderr.on("data", (data) => { stderr += data.toString(); });

    ps.on("error", (error) => {
      reject(new Error(`PowerShell 启动失败: ${error.message}`));
    });

    ps.on("close", (code) => {
      if (code === 0) {
        resolve(stdout.trim());
      } else {
        reject(new Error(stderr.trim() || "PowerShell execution failed"));
      }
    });
  });
}
```

> 注意：批量脚本的 stdout 必须只输出 JSON（避免 `Write-Host`/调试信息），否则解析会失败。

#### convert:documents handler 改造

```
现有流程（串行逐文件）:
  for 每个文件:
    if word → 启动Word → 转PDF → 关闭Word → 渲染PDF
    if ppt  → 启动PPT  → 转PDF → 关闭PPT  → 渲染PDF
    if pdf  → 渲染PDF

改造后流程（批量COM + 逐文件渲染）:
  阶段0: 按类型分组（word / ppt / pdf）

  阶段1: 批量 COM 转换
    wordItems → batchConvertToPdf('word', [...]) → pdf列表  (启动Word一次)
    pptItems  → batchConvertToPdf('ppt', [...])  → pdf列表  (启动PPT一次)

  阶段2: 逐文件渲染 PDF → PNG (所有文件统一为 PDF，串行渲染)
    for 每个 pdf:
      convertPdfBufferToImages() → 输出 PNG
```

**详细伪代码:**

```javascript
ipcMain.handle("convert:documents", async (event, payload) => {

      } else {
        errors.push({ path: item.sourcePath, message: r?.error || 'Word转PDF失败' });
      }

      const r = pptResults.find(pr => pr.id === item.order);
      if (r?.ok) {
        renderQueue.push({ item, pdfPath: r.pdfPath, source: 'ppt' });
      } else {
        errors.push({ path: item.sourcePath, message: r?.error || 'PPT转PDF失败' });
      }
    } else if (ext === ".pdf") {
      renderQueue.push({ item, pdfPath: item.sourcePath, source: 'pdf' });
    }
  }

  // 逐文件渲染
  for (let i = 0; i < renderQueue.length; i++) {
    if (conversionAbortRequested) { /* 取消逻辑 */ break; }
    const { item, pdfPath } = renderQueue[i];
    // ... 现有的 convertItem 渲染逻辑，但直接用 pdfPath ...
  }

  // 清理临时目录
  await fs.promises.rm(batchTempDir, { recursive: true, force: true });

  // ... 返回结果 ...
});
```

## 四、问题三：PNG 压缩级别

### 4.1 现有代码

```javascript
// main.js:1690
return processed.pipeline.png().toBuffer();

// main.js:1631
const buffer = await pipeline.png().toBuffer();
```

sharp 默认 `compressionLevel: 6`（范围 0-9）。两处都未显式指定。

### 4.2 技术原理

**三方一致结论：PNG 是无损压缩，compressionLevel 不影响清晰度。**

| 概念 | 说明 |
|------|------|
| PNG 压缩算法 | DEFLATE（与 ZIP 相同），纯无损 |
| compressionLevel | 控制算法寻找最优编码的"努力程度" |
| 解码后像素 | level 0-9 完全相同，逐像素一致 |
| 对比 JPEG | JPEG 的 quality 参数是有损的，会丢失信息 |

| compressionLevel | 编码速度 | 文件大小 | 清晰度 |
|-----------------|---------|---------|--------|
| 0 (不压缩) | 最快 | 最大 (~2-5x) | 无损 |
| 1 | 很快 | 较大 (~1.1-1.3x) | **无损** |
| 6 (默认) | 适中 | 基准 | 无损 |
| 9 | 最慢 | 最小 (~0.9x) | 无损 |

### 4.3 修改方案

```
修改位置: main.js L1690, L1631
改动量: 各改 1 处参数
风险: 零
```

```javascript
// main.js:1690 (convertPdfBufferToImages 内)
// 现有
return processed.pipeline.png().toBuffer();
// 改为
return processed.pipeline.png({ compressionLevel: 1 }).toBuffer();

// main.js:1631 (postProcessImage 内)
// 现有
const buffer = await pipeline.png().toBuffer();
// 改为
const buffer = await pipeline.png({ compressionLevel: 1 }).toBuffer();
```

### 4.4 Gemini 补充建议

> 可以同时加 `adaptiveFiltering: false` 进一步提速。

评估：`adaptiveFiltering` 控制 PNG 行过滤策略。关闭后：
- 速度略有提升（~5-10%）
- 文件略大（~5%）
- 清晰度不受影响（仍然无损）

**建议：先只改 `compressionLevel: 1`，效果已经很显著。`adaptiveFiltering` 作为后续微调。**

### 4.5 预期收益

以 4000×3000 分辨率页面为例：

| 指标 | level: 6 (现有) | level: 1 |
|------|----------------|----------|
| 编码耗时/页 | ~200ms | ~60ms |
| 文件大小/页 | ~3MB | ~3.5MB |
| 10页总编码 | ~2s | ~0.6s |
| 清晰度 | 无损 | **无损（完全一致）** |

## 五、问题四：并行渲染

### 5.1 当前串行分析

`convertPdfBufferToImages()` (main.js:1648-1698):

```javascript
for (let index = 0; index < limit; index += 1) {
  // 每页完全串行:
  // 1. PDFium 渲染 RGBA       ~100-300ms
  // 2. sharp 处理 + PNG 编码   ~100-200ms  (优化后 ~60ms)
  // 3. writeFile 写磁盘        ~20-50ms
}
```

### 5.2 单页资源消耗

以 4000×3000 分辨率为例：

| 阶段 | 内存 | CPU | 耗时 |
|------|------|-----|------|
| PDFium 渲染 → RGBA buffer | ~48MB (4000×3000×4B) | 单核 100% | ~100-300ms |
| sharp 处理 + PNG 编码 | ~48MB(输入) + ~3.5MB(输出) | 单核 100% | ~60-200ms |
| 写磁盘 | ~3.5MB I/O | 极低 | ~20-50ms |
| **单页合计** | **~100MB 峰值** | - | **~180-550ms** |

### 5.3 并行方案设计

#### A. 页面级并行（同一文件内，推荐并发 2）

```javascript
// 将串行 for 改为分组并发
const PAGE_CONCURRENCY = 2;

async function renderPageBatch(pages, startIndex, options, ...) {
  const batch = pages.slice(startIndex, startIndex + PAGE_CONCURRENCY);
  await Promise.all(batch.map((page, offset) =>
    renderSinglePage(page, startIndex + offset, options, ...)
  ));
}

// 在 convertPdfBufferToImages 中:
for (let i = 0; i < limit; i += PAGE_CONCURRENCY) {
  if (conversionAbortRequested) break;
  await renderPageBatch(pages, i, ...);
}
```

#### B. 文件级并行（多文件同时，推荐并发 2，仅 PDF 渲染阶段）

```javascript
const FILE_CONCURRENCY = 2;

// 在阶段2渲染时:
for (let i = 0; i < renderQueue.length; i += FILE_CONCURRENCY) {
  const batch = renderQueue.slice(i, i + FILE_CONCURRENCY);
  await Promise.all(batch.map(({ item, pdfPath }) =>
    renderPdfToImages(item, pdfPath, options)
  ));
}
```

**注意：** COM 转换阶段（阶段1）保持串行。Office COM 对象是单线程的，强行并行会导致崩溃。

#### C. 综合方案

```
阶段1（串行/批量COM）: Word/PPT → PDF
  └─ 批量脚本，一次 COM 启动

阶段2（文件并行=2 × 页面并行=2）: PDF → PNG
  ├─ file1.pdf: [page1, page2] 同时 → [page3, page4] 同时 → ...
  └─ file2.pdf: [page1, page2] 同时 → [page3, page4] 同时 → ...
  (最多 4 页同时在内存中)
```

### 5.4 资源评估

#### 中低配电脑 (4核 / 8GB RAM)

| 并发配置 | 内存峰值 | CPU 峰值 | 评估 |
|---------|---------|---------|------|
| 页面×1 + 文件×1 (现有) | ~100MB | 1核 100% | 安全 |
| 页面×2 + 文件×1 | ~200MB | 2核 100% | 安全 |
| 页面×2 + 文件×2 | ~400MB | 4核 100%(短暂) | **可接受** |
| 页面×3 + 文件×2 | ~600MB | 6核（超出） | 风险 |

#### 极低配电脑 (2核 / 4GB RAM)

| 并发配置 | 内存峰值 | 占系统比 | 评估 |
|---------|---------|---------|------|
| 页面×2 + 文件×1 | ~200MB | 5% | 安全 |
| 页面×2 + 文件×2 | ~400MB | 10% | **可接受** |
| 页面×3 + 文件×2 | ~600MB | 15% | 不推荐 |

### 5.5 安全措施

```javascript
// 运行时内存检测：可用内存不足时自动降级
const os = require('os');

function getMaxConcurrency() {
  const freeMemMB = os.freemem() / (1024 * 1024);
  const cpuCount = os.cpus().length;

  if (freeMemMB < 500 || cpuCount <= 2) {
    return { pageConcurrency: 1, fileConcurrency: 1 };  // 降级为串行
  }
  return { pageConcurrency: 2, fileConcurrency: 2 };  // 默认有限并发
}
```

### 5.6 Codex 补充观点

> "每页可能接近 60MP，RGBA 内存约 240MB/页；并发 2 页就可能 500MB+。建议默认并发 1，在配置里提供"性能模式"可调到 2。"

**评估：** Codex 按 60MP 上限计算（7746×7746 像素）是最极端场景。实际大多数文档页面在 4000×3000 左右（12MP），内存仅 ~48MB/页。60MP 上限只有 scale≥3 且页面特别大时才会触碰。

**结论：** 并发 2 页在绝大多数场景下安全。不需要配置项，运行时自动检测即可。

### 5.7 预期收益

#### 页面并行（单文件 10 页）

```
串行:     [p1][p2][p3][p4][p5][p6][p7][p8][p9][p10]
并行(2):  [p1,p2][p3,p4][p5,p6][p7,p8][p9,p10]

串行耗时: 10 × 400ms = 4s
并行耗时: 5 × 450ms = 2.25s  (含少量同步开销)
提速: ~40-45%
```

#### 文件并行（10 个文件 × 10 页，结合页面并行）

```
串行文件:
  [file1: 10页][file2: 10页]...[file10: 10页]
  总耗时: 10 × 2.25s = 22.5s

文件并行(2) + 页面并行(2):
  [file1 + file2][file3 + file4]...[file9 + file10]
  总耗时: 5 × 2.5s = 12.5s  (含并发调度开销)
  提速: ~44%

综合（页面×2 + 文件×2 vs 完全串行）:
  完全串行: 10 × 4s = 40s
  双重并行: 5 × 2.5s ≈ 12.5s
  提速: ~69%
```

## 六、补充优化：PPT 直导 PNG

### 6.1 现状

项目中已存在 `ppt-to-png.ps1` (scripts/ppt-to-png.ps1)，但 **当前未被使用**。PPT 走的是 `ppt-to-pdf.ps1` → PDFium 渲染 的路径。

### 6.2 PPT 直导 PNG 的流程

```
现有路径:  PPT → [COM ExportAsFixedFormat] → PDF → [PDFium] → RGBA → [sharp] → PNG
直导路径:  PPT → [COM Export PNG] → PNG → [sharp postProcess] → PNG
```

`ppt-to-png.ps1` 使用 `$presentation.Export($OutputDir, "PNG", $width, $height)`，由 PowerPoint 直接输出 PNG 文件。

### 6.3 评估

| 维度 | 现有路径 (PPT→PDF→PNG) | 直导路径 (PPT→PNG) |
|------|----------------------|-------------------|
| 速度 | 慢（两次转换） | 快（一次转换，省去 PDF 中间步骤） |
| 清晰度 | PDFium 渲染质量高 | PowerPoint 导出质量取决于 COM 参数 |
| 版式一致性 | 高（PDF 是标准格式） | 需验证（复杂动画/渐变可能有差异） |
| 分辨率控制 | 精确（PDFium renderScale） | 受限于 COM Export 的 width/height 参数 |
| 文件命名 | 自己控制 | PowerPoint 自动命名（Slide1.PNG, Slide2.PNG...） |

### 6.4 建议

**暂不使用。** 理由：
1. PPT 直导 PNG 的版式一致性需要大量测试验证
2. 命名由 PowerPoint 控制，需要额外的重命名逻辑
3. 批量 COM + 页面并行的优化已经能覆盖大部分性能诉求
4. 如果后续有需要，可以作为 P3 优化项引入
