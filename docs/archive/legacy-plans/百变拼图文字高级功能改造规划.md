## 一、现状基线（基于真实代码）

### 1.1 字体相关

| 位置 | 现状 |
|------|------|
| `shared/font-config.mjs` | 硬编码 18 条字体配置，`type: "system"` 仅有微软雅黑(win32)、圆体(darwin) |
| `renderer/puzzle/font-loader.js` | 渲染端靠 FontFace API 加载本地字体文件；`type: "system"` 的字体直接视为已加载 |
| `main.js: registerTextFonts()` | 主进程用 `FontLibrary.use(family, paths)` 注册 `type: "local"` 的字体供 skia-canvas 使用 |
| `main.js: verifyFontsAvailable()` | 导出前走 `resolveExportFontFamily(489行) → remap → 探针` 链路，**remap 先于探针执行** |
| `font-config.mjs: EXPORT_FONT_REMAP` | PingFangSC、苹方、Yuanti SC → SourceHanSansCN，**系统字体未列入 remap 时直接透传** |

**导出链路说明：** `verifyFontsAvailable()` 第 489 行先调用 `resolveExportFontFamily(requestedFamily)` 得到 `exportFamily`，只有不在 `EXPORT_FONT_REMAP` 中的字体才会原样透传。当前三个内置字体（PingFangSC/苹方/Yuanti SC）会被 remap 强改，但**系统字体（如微软雅黑、宋体等）不在 remap 中，原样进入探针**，链路正常。**无需改动 remap 逻辑。**

> ⚠️ 风险：若用户选择了名为 `PingFangSC` 的系统字体，remap 会把它改写为 `SourceHanSansCN`，导出结果与预览不一致。但 `PingFangSC` 已在内置字体中，正常用户不会从系统字体列表选到它（因为 `loadSystemFonts()` 会过滤掉内置字体中已有的 family 名）。该风险**可接受，不需要改 remap**。

## 二、功能设计

### 2.1 系统字体

#### 目标
渲染端字体下拉列表 = 内置字体（现有 6 组）+ 系统字体（动态拉取），以 `<optgroup>` 分组显示。

> 注意：当前项目使用 `custom-select` 替代原生 select，默认实现不会显示 optgroup 分组标题。要实现分组展示，需要同步改造 `renderer/puzzle/custom-select.js`（见 4.13）。

#### 数据字段变化
无需改 text.style 结构，`fontFamily` 直接存系统字体 family 名（如 `"微软雅黑"`）。

#### 字重策略
系统字体统一提供 `weights: [400, 700]` 两档，不解析字体文件。

**关键：** 系统字体需合并进 `textFontFamilies` 数组，`syncTextWeightOptions()` 函数（第 1606 行）通过查 `textFontFamilies` 来获取字重列表。若系统字体未合并进去，字重选择器只会显示 [400]（单档回退）。

#### 渲染端加载逻辑（font-loader.js 扩展）

```js
let systemFontCache = null;  // null = 未加载，[] = 已加载但无结果

export async function loadSystemFonts() {
  if (systemFontCache !== null) return systemFontCache;
  if (!window.appApi?.getSystemFonts) {
    systemFontCache = [];
    return [];
  }
  const result = await window.appApi.getSystemFonts();
  if (!result?.ok || !Array.isArray(result.fonts)) {
    systemFontCache = [];
    return [];
  }
  const builtinFamilies = new Set(getPlatformFonts().map(f => f.family));
  // 过滤掉内置字体、去重
  const seen = new Set();
  const deduped = result.fonts
    .filter(name => {
      if (typeof name !== "string" || !name.trim()) return false;
      const trimmed = name.trim();
      if (builtinFamilies.has(trimmed)) return false;
      if (seen.has(trimmed)) return false;
      seen.add(trimmed);
      return true;
    });
  // 限制数量（防止系统字体过多导致下拉渲染卡顿）
  systemFontCache = deduped
    .slice(0, 400)
    .map(name => ({
      family: name.trim(),
      displayName: name.trim(),
      weights: [400, 700],
      isSystem: true
    }));
  return systemFontCache;
}

export function getSystemFontCache() {
  return systemFontCache || [];
}
```

**修改 loadFont() 兼容系统字体**（在 `if (!config) return false;` 之前加分支）：

```js
if (!config) {
```

### 2.2 文字描边

#### 触发逻辑
**无开关字段。** `strokeWidth > 0` 时渲染描边，`strokeWidth = 0`（默认）时不渲染。

#### 新增 style 字段

```js
strokeWidth: 0,          // number，0-20px，默认 0（0 = 不描边）
strokeColor: "#000000"   // string，16进制色值
```

#### normalizeStyle() 扩展

```js
strokeWidth: Math.max(0, Math.min(20, Number(next.strokeWidth) || 0)),
strokeColor: next.strokeColor || "#000000",
```

#### 渲染逻辑

> `ctx.lineWidth` 是线的总宽，文字描边向内向外各一半。UI 上 `strokeWidth=2` → `ctx.lineWidth=4`，视觉描边宽 2px。

渲染顺序：**strokeText（此时带阴影）→ 关闭阴影 → fillText**，避免描边和填充各自叠加阴影。

### 2.3 文字阴影

#### 触发逻辑
**无开关字段。** `shadowBlur > 0 || shadowOffsetX !== 0 || shadowOffsetY !== 0` 时渲染阴影，全为 0（默认）不渲染。

#### 新增 style 字段

```js
shadowColor: "#000000",  // string
shadowBlur: 0,           // number，0-20，默认 0
shadowOffsetX: 0,        // number，-20~20，默认 0
shadowOffsetY: 0         // number，-20~20，默认 0
```

#### normalizeStyle() 扩展

```js
shadowColor: next.shadowColor || "#000000",
shadowBlur: Math.max(0, Math.min(20, Number(next.shadowBlur) || 0)),
shadowOffsetX: Number(next.shadowOffsetX) || 0,
shadowOffsetY: Number(next.shadowOffsetY) || 0,
```

#### 阴影与导出 Scale 的关系

**结论：阴影不需要做 scale 修正，直接透传。**

依据：`createTextLayerBuffer()` 第 617 行使用 `ctx.scale(safeScale, safeScale)`，这会**同时放大坐标系和 shadowOffset/shadowBlur**。这与 `puzzle-render-spec.mjs` 第 187-194 行 `getShadowSpec()` 对坑位阴影的处理一致（乘以 scale factor 放大）。文字阴影随 `ctx.scale` 自动等比放大，与其他视觉元素保持一致，**不需要额外除以 scale**。v1.1 中的反向除法建议是错误的，本版本删除该说明。

#### drawLineWithLetterSpacing() 完整改造

签名从 `(ctx, text, x, y, letterSpacing)` 改为 `(ctx, text, x, y, style)`：

```js
export function drawLineWithLetterSpacing(ctx, text, x, y, style) {
  const value = String(text || "");
  const letterSpacing = Number(style.letterSpacing) || 0;
  const hasStroke = style.strokeWidth > 0;
  const hasShadow = style.shadowBlur > 0 || style.shadowOffsetX !== 0 || style.shadowOffsetY !== 0;
  let cursor = x;

  for (let i = 0; i < value.length; i += 1) {
    const char = value[i];
    const charWidth = ctx.measureText(char).width;

    if (hasStroke) {
      // 描边阶段：若有阴影，此时 ctx.shadow* 已在外层设置，描边触发阴影
      ctx.strokeStyle = style.strokeColor;
      ctx.lineWidth = style.strokeWidth * 2;
      ctx.lineJoin = "round";
      ctx.strokeText(char, cursor, y);
      // 填充前关闭阴影，防止 fillText 再叠一层阴影
      if (hasShadow) {
        ctx.shadowColor = "transparent";
      }
    }

    ctx.fillText(char, cursor, y);

    // 恢复阴影，供下一个字符的描边阶段使用
    if (hasStroke && hasShadow) {
      ctx.shadowColor = style.shadowColor;
    }

    cursor += charWidth + letterSpacing;
  }
}
```

drawText() 中在 `applyTextStyle()` 之后、`lines.forEach` 之前设置阴影：

```js
const hasShadow = style.shadowBlur > 0 || style.shadowOffsetX !== 0 || style.shadowOffsetY !== 0;
if (hasShadow) {
  ctx.shadowColor = style.shadowColor;
  ctx.shadowBlur = style.shadowBlur;
  ctx.shadowOffsetX = style.shadowOffsetX;
  ctx.shadowOffsetY = style.shadowOffsetY;
}
```

drawText() 内调用处同步更新：
```js
// 原：drawLineWithLetterSpacing(ctx, line, drawX, drawY, style.letterSpacing)
// 改：drawLineWithLetterSpacing(ctx, line, drawX, drawY, style)
```

> **各场景：**
> - 只有阴影（无描边）：`ctx.shadow*` 已在外层设置，`fillText` 直接产生阴影，效果正确。
> - 只有描边（无阴影）：正常 `strokeText + fillText`，无副作用。
> - 阴影 + 描边：描边触发阴影，`fillText` 前清除阴影，不重复叠加，效果干净。

## 五、关键风险与注意事项

### 5.1 drawLineWithLetterSpacing 签名变更

该函数是 exported，**必须全局搜索** `drawLineWithLetterSpacing`，确认只有 `drawText()` 内一处调用，无其他调用方，再改签名。

### 5.2 loadStateFromStorage 是持久化恢复的关键路径

`index.js` 第 719-728 行的 `text.style` 枚举与 `template-manager.js` 中的枚举**相互独立**，两处都必须补充新字段。若只改 template-manager 而漏改 loadStateFromStorage，用户重启软件后本地保存的描边/阴影设置会丢失。

### 5.3 系统字体合并进 textFontFamilies 是必须的

`syncTextWeightOptions()` 第 1606 行查的是 `textFontFamilies` 数组。若系统字体只加入了 `<optgroup>` 而未合并进 `textFontFamilies`，用户切换到系统字体后字重选择器会显示单档 400（找不到对应的 weights 数组时的回退值）。改造后 `textFontFamilies` 需要包含内置字体 + 系统字体的完整列表。

### 5.4 custom-select 的 refresh() 是全量重建

`custom-select.js` 第 182-186 行的 `refresh()` 调用 `updateOptions()` → `renderDropdown()`，后者 `dropdown.innerHTML = ''` 全量清空重建 DOM。字体数量多时（系统字体可能数百个）会有明显卡顿。应对方式：系统字体加载完成后只调用一次 `refresh()`，不要频繁调用。当前方案（内置先显示，系统字体异步加载后再 refresh 一次）已满足此要求。

### 5.5 编辑态不支持描边/阴影属于可接受折中

`openTextEditor()` 创建的 textarea 不支持 Canvas 描边/阴影效果。这是「编辑时看不到描边/阴影，确认后显示」的体验。考虑到：
1. CSS `text-shadow` 与 Canvas 阴影效果不完全一致
2. CSS `-webkit-text-stroke` 效果与 Canvas strokeText 有差异（向内裁切）
3. 编辑态的主要目的是输入内容，不是预览最终效果

**不需要在编辑态模拟描边/阴影**，但可在退出编辑时有短暂的视觉跳变，属于可接受的 UX 折中。

### 5.6 optgroup 分组显示依赖 custom-select 改造

`index.html` 中加了 `<optgroup>` 并不代表用户能看到分组标题，因为字体下拉实际渲染由 `custom-select.js` 接管。  
如果不做 4.13 的改造，分组标题不会显示，文档里“分组展示”的产品目标会落空。
