# 清晰度优化方案（文档导出为图片）

## 目标与约束
- 文字边缘清晰，无明显发虚或锯齿
- 单张图片体积不限制（优先质量）
- 保持 3:4 裁剪与倍率放大功能
- Windows 环境下稳定可控

## 现有实现梳理（来自当前代码）
1) Word / PDF
   - `desktop/main.js`：PDFium 渲染时 `page.render({ scale: 1 })`
   - 渲染后由 `sharp.resize` 进行 1.5x / 2x 放大（`applyScaleAndCrop`）
   - 结果：低分辨率先栅格化，再插值放大，文字发虚

2) PPT
   - `desktop/scripts/ppt-to-png.ps1`：`Presentation.Export($OutputDir, "PNG")`
   - 未指定宽高像素，等于使用默认导出分辨率（通常偏低）
   - 结果：文字细节不足，后续放大无效

3) 统一策略缺失
   - UI 的 1x / 1.5x / 2x 实际是“后处理放大”，不是“源头高清渲染”

## 清晰度问题的本质原因
- 栅格化时 DPI 太低，后续放大只会放大模糊边缘
- PPT 默认导出 DPI 低，文字细节丢失

## 统一的高清渲染策略（核心方向）
原则：先高分辨率渲染，再裁剪，再做 PNG 无损编码；尽量不做“放大式插值”。

### 1) Word / PDF：PDFium 高 DPI 渲染
建议把 UI 的倍率与 DPI 绑定，而不是后处理放大。

推荐映射（与 UI 倍率一致，按短边像素控制）：
- 1x -> 约 2500px
- 1.5x -> 约 3300px
- 2x -> 约 4000px
- 3x -> 约 4800px

处理流程：
1) PDFium 按目标 DPI 渲染
2) 3:4 居中裁剪
3) PNG 无损编码
4) 不做体积限制下采样

### 2) PPT：导出阶段直接指定像素大小
推荐直接用 Export 的宽高参数，避免默认 DPI。

计算公式：
- widthPx = SlideWidthPoints / 72 * TargetDPI
- heightPx = SlideHeightPoints / 72 * TargetDPI

TargetDPI 根据短边像素与页面尺寸动态换算。

可选方案（备用）：
- PPT -> PDF -> 走 PDFium 同一渲染链路
  - 优点：渲染一致性高
  - 缺点：转换多一步，耗时略高

### 3) Word -> PDF：确保“打印质量”
Word 导出 PDF 时应使用打印优化模式，避免 PDF 本身被降质。
建议明确 `ExportAsFixedFormat` 使用 “OptimizeForPrint”。

## 体积控制（已关闭）
当前策略为“质量优先，体积不限制”，不做下采样与体积限制。

## 裁剪与顺序（必须固定）
1) 源头高 DPI 渲染
2) 3:4 居中裁剪
3) PNG 无损编码
4) 不做体积限制下采样

这样顺序可确保清晰度最大化，且不做体积限制下采样。

## 速度与内存优化（已实施）
- PDF 渲染前估算像素量并设置上限（约 60MP），避免 900 DPI 时内存峰值过高
- PPT 导出在计算目标像素后同样设置像素上限，降低导出时内存占用
- 导出流程增加阶段提示：Word 转 PDF / PDF 渲染 / PPT 导出 / 图片后处理

## 验收标准（可直接用于测试）
- 100% 放大查看时，红色细字不发虚
- A4 宽度像素 >= 2480px（300 DPI 参考）
- 单张图片体积不限制
- 1x / 1.5x / 2x / 3x 清晰度随倍率明显提升

## 风险与注意事项
- 高 DPI 会增加 CPU 与内存占用，需要评估大批量文件的耗时
- PPT 导出依赖 Office COM；WPS 可能无法稳定指定像素
- 体积不限制时无需下采样

## 实施位置（对应代码）
- PDF 渲染：`desktop/main.js -> convertPdfBufferToImages() -> page.render({ scale })`
- PPT 导出：`desktop/scripts/ppt-to-png.ps1 -> Presentation.Export(...)`
- Word 导出：`desktop/scripts/word-to-pdf.ps1 -> ExportAsFixedFormat(OptimizeForPrint)`
- 体积控制：已关闭
