# 飞书一键上传 — 按笔记上传模式产品开发方案

## 一、文档目的

本文档用于规划「飞书一键上传」模块新增 **按笔记上传** 模式的产品与开发方案。

当前飞书上传能力是「分模块上传」：

- 用户配置多个图片文件夹
- 每个文件夹独立设置上传方式与每行数量
- 每一行从多个文件夹取图后合并写入同一个飞书附件字段

本次新增模式是「按笔记上传」：

- 用户可以选择 1 个父文件夹作为扫描入口
- 用户也可以选择多个入口文件夹，组合成一批笔记来源
- 每个入口文件夹支持递归扫描其子文件夹
- 扫描结果以 **最下层子文件夹** 作为笔记列表
- 用户可以从笔记列表中删除某篇笔记
- 每篇笔记上传到飞书表格的一行
- 笔记文件夹内图片整体上传到该行的附件字段

目标是新增模式，不破坏现有「分模块上传」能力。

## 二、当前软件功能与上传现状

## 2.1 当前软件主功能

当前桌面软件主要包含以下模块：

| 模块 | 说明 |
|---|---|
| 文档一键导出 | Word / PPT / PDF 批量导出 PNG |
| 场景化图片排版 | 背景图与叠图透视合成 |
| 百变拼图排版 | 模板坑位批量生成图片 |
| 飞书一键上传 | 批量上传图片到飞书多维表格附件字段 |
| 小红书商品下载 | 抓取商品主图与详情图 |
| 设置 | 授权、日志、版本与运行配置 |

## 2.2 当前飞书上传实现

当前上传模式可定义为：

```text
分模块上传
```

核心状态：

```javascript
const uploadState = {
  folders: [],
  nextFolderId: 1
};
```

单个文件夹配置：

```javascript
{
  id: 1,
  path: "D:\\素材\\产品图",
  mode: "sequential", // sequential | random
  count: 1
}
```

当前上传逻辑：

1. 用户填写飞书授权码、表格链接、附件字段、起始行、结束行
2. 用户添加一个或多个图片文件夹
3. 每个文件夹可选择：
   - 顺序上传
   - 随机上传
   - 每行上传几张
4. 点击开始后，按行处理
5. 每行从所有文件夹中取图
6. 将该行所有图片合并写入同一个附件字段

现有能力应完整保留。

## 三、新模式定义

## 3.1 新增上传模式

飞书一键上传新增两种互斥模式：

| 模式名称 | 标识 | 说明 |
|---|---|---|
| 分模块上传 | `module` | 当前已有能力，多文件夹按每行数量合并上传 |
| 按笔记上传 | `note-folder` | 选择一个或多个入口文件夹，扫描最下层子文件夹作为笔记 |

默认模式建议：

```text
分模块上传
```

原因：

- 兼容当前用户习惯
- 避免升级后用户进入页面发现配置区变化过大
- 新模式通过显式切换进入

## 3.2 上传模式 UI 规则

上传模式做成左右切换 Tab：

```text
+--------------------------------------------------+
| 上传模式                                          |
| +----------------------+ +----------------------+ |
| | 分模块上传           | | 按笔记上传           | |
| +----------------------+ +----------------------+ |
+--------------------------------------------------+
```

交互规则：

- 左右 Tab 二选一
- 当前激活 Tab 使用高亮样式
- 切换 Tab 不清空另一个模式已经配置的内容
- 默认打开 `分模块上传`
- `分模块上传` 保持现有配置区
- `按笔记上传` 显示入口文件夹与笔记列表配置区

## 3.3 按笔记上传的核心规则

按笔记上传时，目录来源不再限定为单个父文件夹第一层子目录，而是：

```text
入口文件夹集合
  ↓
递归扫描每个入口文件夹
  ↓
找到最下层子文件夹
  ↓
最下层子文件夹 = 一篇笔记
```

示例一：选择一个父文件夹

```text
父文件夹
├─ 账号A
│  ├─ 笔记001
│  │  ├─ 01.png
│  │  └─ 02.png
│  └─ 笔记002
│     └─ 01.png
└─ 账号B
   └─ 笔记003
      └─ 01.png
```

扫描结果：

```text
笔记001
笔记002
笔记003
```

示例二：直接选择多个子文件夹

```text
用户选择:
  D:\批次\账号A
  D:\批次\账号B

账号A
├─ 笔记001
└─ 笔记002

账号B
├─ 笔记003
└─ 笔记004
```

扫描结果：

```text
笔记001
笔记002
笔记003
笔记004
```

解释：

- 入口文件夹只是扫描入口，不必然等于笔记
- 有子文件夹时，继续向下找最下层子文件夹
- 最下层子文件夹内的图片代表这篇笔记的图片内容
- 每个有效笔记文件夹写入飞书表格一行
- 用户可从生成后的笔记列表中删除某篇笔记

## 3.4 已确认交互规则

按笔记上传入口选择采用以下规则：

| 交互 | 决策 |
|---|---|
| 点击 `选择父文件夹` | 替换当前入口列表，适合重新选择一个完整批次 |
| 点击 `添加多个子文件夹` | 追加到当前入口列表，适合补充部分账号、类目或笔记组 |
| 重复选择同一个入口 | 不重复添加，给出一次轻提示 |
| 选择入口后是否自动扫描 | 自动扫描，同时保留 `重新扫描` 按钮 |
| 入口顺序调整 | 不提供手动上移 / 下移；顺序由选择或追加顺序决定 |
| 单篇笔记顺序调整 | 第一版不支持上移 / 下移，只支持删除 |
| 删除笔记后如何恢复 | 点击 `重新扫描` 恢复完整笔记列表 |

说明：

- 入口顺序直接决定飞书行号，一期按用户选择或追加入口的顺序固定生成。
- 单篇笔记列表数量可能很多，第一版只提供删除，避免 UI 和状态复杂度过高。
- 自动扫描可以减少用户操作；重新扫描用于恢复误删笔记或刷新本地目录变化。

## 3.5 最下层子文件夹定义

最下层子文件夹，也叫叶子文件夹：

```text
该文件夹下面没有更深一层的子文件夹
```

示例：

```text
父文件夹
├─ A
│  ├─ A-1
│  │  └─ 01.png
│  └─ A-2
│     └─ 01.png
└─ B
   └─ 01.png
```

叶子文件夹：

```text
A-1
A-2
B
```

其中 `B` 虽然是第一层子文件夹，但因为它下面没有更深子文件夹，所以它也是叶子文件夹。

## 3.6 已确认规则：笔记到飞书行的映射

已确认采用：

```text
入口顺序优先，入口内部自然排序
第 1 个有效笔记 -> 起始行
第 2 个有效笔记 -> 起始行 + 1
第 3 个有效笔记 -> 起始行 + 2
```

示例：

```text
入口文件夹:
  1. D:\批次\账号B
  2. D:\批次\账号A

账号B 内部笔记:
  1-家居
  2-家居

账号A 内部笔记:
  1-穿搭
  2-护肤
  10-家居

起始行 = 2

映射:
  账号B / 1-家居 -> 第 2 行
  账号B / 2-家居 -> 第 3 行
  账号A / 1-穿搭 -> 第 4 行
  账号A / 2-护肤 -> 第 5 行
  账号A / 10-家居 -> 第 6 行
```

排序要求：

- 入口文件夹顺序以用户添加顺序为准
- 同一入口内部的叶子笔记按相对路径自然排序
- `2` 排在 `10` 前面
- 不同入口之间不做全局自然排序
- 同一路径重复出现时，只保留首次出现的笔记
- 用户删除某篇笔记后，剩余笔记重新连续映射行号

## 四、产品边界规则

## 4.1 扫描范围

按笔记上传扫描：

```text
一个或多个入口文件夹
递归查找每个入口下的最下层子文件夹
读取每个最下层子文件夹中的第一层图片
```

递归只用于查找最下层子文件夹。

图片读取仍只读取笔记文件夹第一层图片，不继续读取笔记文件夹内更深层目录。

示例：

```text
父文件夹
├─ 账号A
│  ├─ 笔记A
│  │  ├─ 01.png        计入
│  │  ├─ 02.jpg        计入
│  │  └─ 过程图
│  │     └─ 03.png     不计入
│  └─ 笔记B
│     └─ 01.png        计入
└─ 账号B
   └─ 笔记C
      └─ 01.png        计入
```

采用“递归找叶子 + 叶子内不递归取图”的原因：

- 支持用户按账号、类目、批次分层管理笔记
- 仍能避免把笔记内部临时目录、过程目录误上传
- 上传前预览更容易解释
- 最终上传单位稳定落在叶子文件夹

## 4.2 有效笔记

有效笔记定义：

```text
最下层子文件夹，并且该文件夹第一层目录内至少有 1 张支持格式的图片
```

有效笔记参与：

- 行映射
- 总图片数统计
- 上传任务

无图片叶子文件夹不参与行映射，进入跳过列表。

## 4.3 图片格式

复用当前全局图片格式集合：

```text
.png
.jpg
.jpeg
.webp
.bmp
.gif
.tif
.tiff
.svg
.ico
.jfif
.pjpeg
.pjp
.avif
.apng
```

非图片文件忽略，不报错。

## 4.4 子文件夹内图片排序

每篇笔记内图片按文件名自然排序上传。

示例：

```text
1.png
2.png
10.png
```

上传顺序为：

```text
1.png -> 2.png -> 10.png
```

如果文件名相同理论上不可能出现在同一目录；如跨目录同名，不影响，因为每篇笔记单独处理。

## 4.5 入口文件夹自身图片

入口文件夹自身图片是否上传，需要按入口文件夹是否为叶子来判断。

推荐规则：

| 场景 | 是否作为笔记 | 说明 |
|---|---|---|
| 入口文件夹下面还有子文件夹 | 否 | 入口只是容器，其自身图片忽略 |
| 入口文件夹下面没有子文件夹，但自身有图片 | 是 | 入口本身就是最下层文件夹 |
| 入口文件夹下面没有子文件夹，也没有图片 | 否 | 无有效内容，进入跳过 |

示例一：入口只是容器

```text
入口文件夹
├─ cover.png
├─ 笔记A
│  └─ 01.png
└─ 笔记B
   └─ 01.png
```

结果：

```text
cover.png 不上传
笔记A 作为笔记
笔记B 作为笔记
```

示例二：入口本身就是笔记

```text
入口文件夹
├─ 01.png
├─ 02.png
└─ 03.png
```

结果：

```text
入口文件夹作为 1 篇笔记
```

UI 扫描结果中可提示：

```text
有子文件夹的入口目录，其根部图片不会上传
```

## 4.6 空叶子文件夹

空叶子文件夹或无支持图片的叶子文件夹：

- 不上传
- 不占用飞书行
- 出现在扫描预览的“跳过”状态中

示例：

```text
入口文件夹:
  1-穿搭    3张
  2-护肤    0张
  3-家居    2张

起始行 = 2

映射:
  1-穿搭 -> 第 2 行
  3-家居 -> 第 3 行

跳过:
  2-护肤，无可用图片
```

## 4.7 隐藏文件和系统文件

第一版建议不额外处理隐藏文件属性，只按扩展名判断是否图片。

原因：

- Windows 隐藏属性判断会增加平台差异
- 当前其他模块也是以扩展名和文件类型为核心
- 用户一般不会把隐藏图片放入内容目录

如果后续有误传问题，再增加“忽略隐藏文件”开关。

## 4.8 快捷方式与异常目录

第一版不跟随快捷方式。

规则：

- 只有真实目录参与子文件夹扫描
- 快捷方式 `.lnk` 视为普通非图片文件，忽略
- 无权限读取的子文件夹进入错误列表，不参与上传

## 4.9 多入口文件夹去重

按笔记上传支持选择多个入口文件夹，因此可能出现包含关系：

```text
已选择:
  D:\批次
  D:\批次\账号A
```

这会导致 `账号A` 下的叶子笔记被扫描两次。

推荐规则：

- 以笔记文件夹完整路径作为唯一键
- 扫描结果去重
- 同一路径只保留第一次出现的笔记
- 因为整体顺序是入口顺序优先，所以重复笔记保留靠前入口中的那一份
- UI 可提示“已自动去重 N 篇重复笔记”

入口文件夹本身也建议去重：

- 用户重复选择同一路径时不重复添加
- 如果新选择的入口已经被已有入口覆盖，仍允许添加，但最终笔记列表去重
- 后续如需更强提示，可在添加入口时提示“该目录已包含在某个入口中”

## 4.10 删除笔记列表项

按笔记上传支持删除某个笔记列表项。

删除规则：

- 删除只影响当前待上传列表
- 不删除本地文件夹
- 不删除入口文件夹
- 删除后重新计算：
  - 有效笔记数
  - 图片总数
  - 结束行
  - 每篇笔记映射行号

示例：

```text
删除前:
  A -> 第 2 行
  B -> 第 3 行
  C -> 第 4 行

删除 B 后:
  A -> 第 2 行
  C -> 第 3 行
```

恢复方式：

- 第一版不做撤销
- 用户可以点击“重新扫描”恢复完整列表

## 4.11 单篇笔记图片数量上限

第一版不做硬上限。

但 UI 需要在扫描预览中展示每篇图片数，便于用户自己判断。

后续如遇飞书接口或性能限制，再增加：

```text
每篇最多上传 N 张
超出部分跳过 / 阻断
```

## 五、飞书表格规则

## 5.1 基础字段

按笔记上传继续复用现有字段：

| 字段 | 说明 |
|---|---|
| 授权码 | 飞书 PersonalBaseToken |
| 表格链接 | 多维表格链接，需包含 app_token、table、view |
| 飞书附件字段 | 写入图片附件的字段名 |
| 起始行 | 第一篇有效笔记写入的行号 |

## 5.2 结束行处理

按笔记上传模式下，不建议让用户手动维护结束行。

推荐规则：

```text
结束行 = 起始行 + 有效笔记数 - 1
```

UI 展示：

```text
将写入第 2 行至第 16 行，共 15 篇笔记
```

如果保留现有 `endRow` 输入，应在按笔记模式下只读或隐藏。

推荐实现：

- 分模块上传：显示起始行、结束行
- 按笔记上传：显示起始行，结束行自动计算并以文本展示

## 5.3 行数不足

如果飞书表格可读取记录数不足：

```text
记录数 < 起始行 + 有效笔记数 - 1
```

则上传前阻断。

错误提示：

```text
飞书表格行数不足：需要写入到第 X 行，但当前视图只读取到 Y 行
```

不建议自动新增行。

原因：

- 当前 Feishu API 封装没有新增记录能力
- 自动增行会引入字段默认值、视图过滤、排序等额外风险
- 当前已有逻辑也是行范围超出时阻断

## 5.4 附件写入策略

第一版建议沿用现有行为：

```text
追加附件
```

即：

```javascript
[fieldName]: [...existingAttachments, ...newAttachments]
```

原因：

- 与当前分模块上传行为一致
- 不会误删用户已有附件
- 风险最低

后续可以新增高级开关：

| 写入方式 | 说明 |
|---|---|
| 追加附件 | 保留原附件，在末尾追加新图片 |
| 覆盖附件 | 清空原附件，只保留本次上传图片 |

第一版不建议上覆盖能力，避免误操作。

## 5.5 是否写入笔记标题字段

第一版建议不做标题字段写入，只写附件字段。

原因：

- 当前 UI 只有附件字段配置
- 用户的标题字段名称、字段类型不一定统一
- 标题同步涉及另一个字段校验链路

建议作为第二阶段能力：

```text
可选：将子文件夹名写入指定文本字段
```

届时新增字段：

- 是否写入笔记标题
- 标题字段名
- 写入方式：覆盖 / 仅为空时写入

## 六、前端 UI 方案

## 6.1 总体结构

上传页结构建议调整为：

```text
飞书基础配置
  授权码
  表格链接
  附件字段

上传模式
  左右 Tab：[分模块上传] [按笔记上传]

行设置
  分模块上传：起始行 + 结束行
  按笔记上传：起始行 + 自动结束行说明

模式配置区
  分模块上传：当前多文件夹配置
  按笔记上传：入口文件夹选择 + 叶子笔记列表预览

操作区
  开始一键上传 / 取消 / 状态 / 进度条
```

## 6.2 模式切换 Tab

使用左右 Tab：

```text
+--------------------------------------------------+
| 上传模式                                          |
| +----------------------+ +----------------------+ |
| | 分模块上传           | | 按笔记上传           | |
| +----------------------+ +----------------------+ |
+--------------------------------------------------+
```

显示文案：

- 分模块上传：多个图片文件夹按每行数量合并写入
- 按笔记上传：扫描最下层子文件夹作为笔记逐行写入

切换规则：

- 切换模式不清空另一模式配置
- 两套配置在内存中独立保存
- 不持久化本地文件夹路径，延续当前隐私策略

## 6.3 分模块上传配置区

保持现状：

- 添加文件夹
- 每个文件夹选择路径
- 顺序上传 / 随机上传
- 每行数量
- 空状态提示

- 删除单篇笔记后：不重新扫描，只对当前待上传列表重排飞书行号
- 点击 `重新扫描`：按当前入口列表重新扫描，并恢复被删除的笔记

## 九、按笔记上传主流程

## 9.1 前端流程

```text
用户切换到按笔记上传
  ↓

  ↓

  ↓

  ↓
```

## 9.2 主进程流程

```text
handleFeishuNoteFolderUpload
  ↓
校验 token/link/field/startRow/noteGroups
  ↓
解析飞书链接
  ↓
校验附件字段存在且 type=17
  ↓
计算 endRow = startRow + noteGroups.length - 1
  ↓
读取飞书记录到 endRow
  ↓
如果记录数不足，阻断
  ↓
逐篇笔记处理
    ↓
    当前 noteGroup 对应 record
    ↓
    逐张图片上传 drive media
    ↓
    收集 file_token
    ↓
    合并 existingAttachments
  ↓
batchUpdateRecords
  ↓
返回 uploaded / failed / recordIds
```

## 9.3 伪代码

```javascript
async function handleFeishuNoteFolderUpload(event, payload) {
  uploadAbortRequested = false;

  const token = payload.token;
  const link = payload.link;
  const fieldName = payload.fieldName;
  const startRow = Number(payload.startRow);
  const noteGroups = payload.noteGroups;

  validateBasicPayload();

  const domain = payload.domain || "https://base-api.feishu.cn";
  const { appToken, tableId, viewId } = parseBaseLink(link);

  const fields = await listFields(domain, token, appToken, tableId, viewId);
  const field = fields.find((item) => item.field_name === fieldName);
  validateAttachmentField(field);

  const endRow = startRow + noteGroups.length - 1;
  const records = await listRecords(domain, token, appToken, tableId, viewId, endRow);
  validateRecordCount(records, endRow);

  const totalImages = noteGroups.reduce((sum, group) => sum + group.images.length, 0);
  sendProgress("upload:progress", { phase: "start", total: totalImages });

  const updates = [];
  let imageIndex = 0;
  let successCount = 0;
  const failedFiles = [];

  for (let groupIndex = 0; groupIndex < noteGroups.length; groupIndex += 1) {
    const group = noteGroups[groupIndex];
    const rowNumber = startRow + groupIndex;
    const record = records[rowNumber - 1];
    const existingAttachments = record.fields?.[fieldName] || [];
    const rowFileTokens = [];

    for (const image of group.images) {
      if (uploadAbortRequested) {
        sendProgress("upload:progress", { phase: "cancelled" });
        return { ok: false, cancelled: true };
      }

      imageIndex += 1;
      sendProgress("upload:progress", {
        phase: "file-start",
        currentIndex: imageIndex,
        total: totalImages,
        fileName: image.name,
        noteName: group.name,
        rowNumber
      });

      try {
        const parentType = getBitableParentType(image.path);
        const fileToken = await uploadDriveFile(domain, token, image.path, parentType, appToken);
        rowFileTokens.push({ file_token: fileToken });
        successCount += 1;
      } catch (error) {
        failedFiles.push({ file: image.name, noteName: group.name, rowNumber, error });
      }
    }

    if (rowFileTokens.length > 0) {
      updates.push({
        record_id: record.record_id,
        fields: {
          [fieldName]: [...existingAttachments, ...rowFileTokens]
        }
      });
    }
  }

  if (updates.length > 0) {
    await batchUpdateRecords(domain, token, appToken, tableId, updates);
  }

  return {
    ok: true,
    uploaded: successCount,
    failed: failedFiles.length
  };
}
```

## 十、错误与边界处理

## 10.1 前端阻断错误

| 场景 | 处理 |
|---|---|
| 授权码为空 | 阻断，提示填写授权码 |
| 表格链接为空或非 https | 阻断，提示链接不合法 |
| 附件字段为空 | 阻断，提示填写字段 |
| 起始行非法 | 阻断，提示行范围不合法 |
| 未选择入口文件夹 | 阻断，提示选择父文件夹或添加子文件夹 |
| 扫描后有效笔记数为 0 | 阻断，提示无可上传笔记 |
| 有效图片数为 0 | 阻断，提示无可上传图片 |

## 10.2 主进程阻断错误

| 场景 | 处理 |
|---|---|
| 入口路径不存在 | 扫描失败，提示路径不可访问 |
| 入口路径不是目录 | 扫描失败 |
| 读取目录无权限 | 扫描失败或单组跳过 |
| 飞书字段不存在 | 上传失败，提示未找到对应字段 |
| 字段不是附件类型 | 上传失败，提示字段类型不是附件 |
| 飞书记录数不足 | 上传失败，提示行数不足 |
| noteGroups 为空 | 上传失败 |
| group.images 为空 | 主进程兜底过滤或报错 |

## 10.3 部分图片上传失败

沿用当前行为：

- 单张失败不终止整个任务
- 记录失败文件
- 继续上传后续图片
- 最终返回 `failed`
- 能成功上传的图片仍写入飞书

注意：

如果某篇笔记全部图片失败，则该行不更新附件字段。

## 10.4 batchUpdate 失败

如果图片上传成功，但最后批量更新飞书记录失败：

- 返回失败
- 日志说明：图片已上传到飞书素材，但附件字段写入失败
- 第一版不做自动回滚

原因：

- 飞书媒体上传成功后无法简单删除
- 当前模块也没有回滚机制

## 10.5 取消上传

取消规则：

- 点击取消后设置 `uploadAbortRequested = true`
- 当前正在上传的单张图片无法中断时，等待该请求结束
- 下一次循环检查到取消后返回
- 已上传并已加入 updates 但尚未 batchUpdate 的内容：
  - 如果取消发生在 batchUpdate 前，默认不提交剩余 updates
  - 如果取消发生在 batchUpdate 后，则已写入内容保留

第一版保持当前取消语义，不做复杂回滚。

## 10.6 重复执行

第一版重复执行会继续追加附件。

风险：

- 同一篇笔记图片会重复出现在附件字段

缓解方式：

- 上传前文案说明“默认追加”
- 后续版本增加“覆盖附件”模式

## 十六、最终结论

本次改造应采用“双模式上传”设计：

```text
飞书一键上传
├─ 分模块上传
└─ 按笔记上传
```

按笔记上传的最小闭环是：

1. 通过左右 Tab 切换到按笔记上传
2. 选择一个父文件夹，或添加多个入口文件夹
3. 递归扫描入口文件夹
4. 以最下层子文件夹作为笔记
5. 过滤无图叶子文件夹，并按完整路径去重
6. 支持从待上传笔记列表删除某篇笔记
7. 按入口顺序优先、入口内部自然排序，从起始行开始逐行映射
8. 每篇笔记内图片自然排序后全部上传
9. 追加写入飞书附件字段

该方案可以最大化复用现有飞书上传 API 层，同时把新业务语义控制在上传模块内部，不影响文档导出、拼图、场景化排版和小红书下载模块。
